### Ver.1.1以降へ延期可能

#### `-32001`(Server overloaded)の安全な自動再試行

現状でもエラー表示はできるため機能は壊れておらず、再試行の実装ミスは二重実行の危険を伴う。急いで実装する理由が無いと判断し延期。

前提として、`RpcFailure`へJSON-RPCのcode/dataを保持できるようにする必要がある(現状は`server_rejected`がエラー全体を文字列化しているだけで、`message`の文字列検索で`-32001`を判定するのは不安全)。

```rust
pub struct RpcFailure {
    pub kind: RpcFailureKind,
    pub message: String,
    pub code: Option<i64>,
    pub data: Option<serde_json::Value>,
}
```

再試行してよいRPCは許可リスト(ブロックリストではない)で管理する。`thread/list`・`thread/read`・`model/list`・`account/rateLimits/read`は対象、`thread/start`・`turn/start`・承認応答・`thread/name/set`は対象外(二重実行につながるため)。

#### `App.tsx`の全面的なcomponent／custom hook分割

項目1の`notificationReducer.ts`抽出（未完了）が前提。労力の割に得られる価値が今は薄い（動作は理解できる形で保たれており、Ver.1.0前に優先すべきは実GUI試験）と判断し延期。

```text

hooks/useCodexNotifications.ts
hooks/useThreads.ts
hooks/useTurn.ts
hooks/useApprovals.ts
hooks/useProjectDiscovery.ts

```

状態管理ライブラリの導入は不要、custom hookへの分離で十分。

**スキーマ検証の二段階化**: [schemas.ts](../app/src/schemas.ts)の`ThreadItemSchema`を、既知型（`userMessage`/`agentMessage`/`reasoning`/`commandExecution`/`fileChange`）は詳細スキーマで厳密検証、未知typeはid/typeのみの汎用スキーマへフォールバックする二段階構成にした。`type`の値をまず見て対応スキーマ（`KNOWN_ITEM_SCHEMAS`ルックアップ）を選ぶため、既知型の不正データ（例: `agentMessage.text`欠落）が未知型スキーマへ誤ってフォールバックすることはない。[schemas.test.mjs](../app/src/schemas.test.mjs)で「既知型の壊れたデータは失敗する／未知typeは汎用スキーマを通る」の両方を固定した。
