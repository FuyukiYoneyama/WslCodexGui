### P1

#### 5. スキーマ検証をより深く(既知/未知の二段階)

**完了（2026-07-23）**: [schemas.ts](../app/src/schemas.ts)の`ThreadItemSchema`を、既知型（`userMessage`/`agentMessage`/`reasoning`/`commandExecution`/`fileChange`）は詳細スキーマで厳密検証、未知typeはid/typeのみの汎用スキーマへフォールバックする二段階構成にした。`type`の値をまず見て対応スキーマ（`KNOWN_ITEM_SCHEMAS`ルックアップ）を選ぶため、既知型の不正データ（例: `agentMessage.text`欠落）が未知型スキーマへ誤ってフォールバックすることはない。[schemas.test.mjs](../app/src/schemas.test.mjs)で「既知型の壊れたデータは失敗する／未知typeは汎用スキーマを通る」の両方を固定した。

`zod`はdiscriminatedUnionではなく、`type`文字列を見てスキーマを選択する`superRefine`ベースの手書きロジックを採用（discriminatedUnion単体だと「型は一致するが中身が壊れている」場合と「型自体が未知」の場合をエラーコードだけで安全に区別するのがv4のissue形状に依存しすぎるため）。

型アサーションが残っていた箇所も併せてzod検証を追加した:
- `thread/tokenUsage/updated` → `ThreadTokenUsageUpdatedSchema`
- `model/list` → `ModelListResponseSchema`
- `account/rateLimits/read` → `GetAccountRateLimitsResponseSchema`
- `gitDiffToRemote`の結果 → `GitDiffToRemoteResponseSchema`

### P2

#### 7. `-32001`(Server overloaded)の再試行

現状でもエラー表示はできるため機能は壊れておらず、再試行の実装ミスは二重実行の危険を伴う。優先度は中。

前提として、`RpcFailure`へJSON-RPCのcode/dataを保持できるようにする必要がある(現状は`server_rejected`がエラー全体を文字列化しているだけで、`message`の文字列検索で`-32001`を判定するのは不安全)。

```rust
pub struct RpcFailure {
    pub kind: RpcFailureKind,
    pub message: String,
    pub code: Option<i64>,
    pub data: Option<serde_json::Value>,
}
```

再試行してよいRPCは許可リスト(ブロックリストではない)で管理する。`thread/list`・`thread/read`・`model/list`・`account/rateLimits/read`は対象、`thread/start`・`turn/start`・承認応答・`thread/name/set`は対象外(二重実行につながるため)。
