### Ver.1.1以降へ延期可能

#### `-32001`(Server overloaded)の安全な自動再試行

現状でもエラー表示はできるため機能は壊れておらず、再試行の実装ミスは二重実行の危険を伴う。急いで実装する理由が無いと判断し延期。

前提として、`RpcFailure`へJSON-RPCのcode/dataを保持できるようにする必要がある(現状は`server_rejected`がエラー全体を文字列化しているだけで、`message`の文字列検索で`-32001`を判定するのは不安全)。

```rust
pub struct RpcFailure {
    pub kind: RpcFailureKind,
    pub message: String,
    pub code: Option<i64>,
    pub data: Option<serde_json::Value>,
}
```

再試行してよいRPCは許可リスト(ブロックリストではない)で管理する。`thread/list`・`thread/read`・`model/list`・`account/rateLimits/read`は対象、`thread/start`・`turn/start`・承認応答・`thread/name/set`は対象外(二重実行につながるため)。

##### 前提の見直し

`仕様書.md`1.3節（非目的）には「Windows ネイティブ実行のCodex（WSLを介さない実行）のサポート」が挙がっている。これは1.1節の背景「Windows版公式アプリ（GUI）は不安定」を理由にしたものだが、**「公式アプリ（GUI）」と「codex CLI自体のネイティブWindowsバイナリ」は別物**であることが分かった。npmレジストリを確認したところ、`@openai/codex`は`optionalDependencies`として`@openai/codex-win32-x64`・`@openai/codex-win32-arm64`を公式配布しており、非公式のハックではない。この非目的の記述は、実態に即して将来的に見直す余地がある。

##### 実機検証で確認できたこと（2026-07-27）

ユーザーの環境に既にWindows側へcodex CLI（`codex-cli 0.144.6`、`C:\Users\user\AppData\Roaming\npm\codex.cmd`）が導入済みだったため、wsl.exeを一切介さずNode.jsから直接`codex app-server`を起動し、`initialize`→`thread/start`（`sandbox: workspace-write`明示）→`turn/start`→コマンド実行→`turn/completed`まで一通り実行して成功を確認した。

```
userAgent: probe/0.144.6 (Windows 10.0.19045; x86_64) ...
sandbox: {"type":"workspaceWrite","writableRoots":[],"networkAccess":false,...}
実行コマンド: "C:\Program Files\PowerShell\7\pwsh.exe" -Command 'echo hello-from-native-windows-codex'
exitCode: 0, 出力: hello-from-native-windows-codex
```

分かった注意点:

- **`.cmd`ファイルのspawn**: Node.jsの`child_process.spawn()`で`codex.cmd`を直接渡すと`EINVAL`になり`shell: true`が必要だった。Rust（`std::process::Command`）でも同様の配慮が要る（`cmd.exe /c`経由にする、または拡張子なしの`codex`シムを使う等、実装時に要検証）。
- **コマンド実行系統がWSL版と異なる**: WSL版は`bash -lc '...'`、ネイティブ版は`pwsh.exe -Command '...'`で実行される。承認モーダルのコマンド表示欄など、ユーザーに見せる文字列の見た目が変わる。
- **軽微なstderr警告**: `failed to load models cache: missing field 'supports_reasoning_summaries'`が出たが動作に支障はなかった（Windows側0.144.6とWSL側0.145.0のバージョン差によるモデルキャッシュ形式の非互換と推測、実害なし）。
- 承認レベル・サンドボックス設定など、既存の`thread/start`パラメータはネイティブ側でも同様に機能した。

##### アーキテクチャ方針

`rpc_request`／`respond_server_request`／`reject_server_request`（[lib.rs](../app/src-tauri/src/lib.rs)）はプロセスの起動方法を一切知らない、プロトコル層として独立している。プロセス起動を担う唯一の箇所は[`Connection::spawn`](../app/src-tauri/src/appserver.rs)内の

```rust
let mut cmd = Command::new("wsl.exe");
cmd.args(["-d", distro, "--exec", codex_path, "app-server"]);
```

のみであり、ここを接続方式で分岐させれば、以降のRPCハンドリングは無改造で流用できる。既存のWSLフローを壊さないよう、**「接続方式（WSL／Windows-native）」を明確に分けたトグルとして追加し、内部処理も分岐させる**方針とする（1つのコードパスに無理に統合しない）。

##### 変更が必要な箇所

| 箇所 | 現状 | ネイティブ時に必要な変更 |
|---|---|---|
| 接続コマンド（`connect`/`Connection::spawn`） | `wsl.exe -d <distro> --exec <codex_path> app-server` | 接続方式が`native`なら`Command::new(codex_path)`＋`.arg("app-server")`を直接起動（`.cmd`拡張子対応の検証込み） |
| WSLディストリ選択 | `list_wsl_distros`/`validate_distro` | ネイティブ時は非表示。接続方式トグルの新設が前提 |
| codexパス欄・検出/検証 | `detect_codex_path`/`verify_codex_path`がwsl.exe経由でWSL絶対パスを検証 | ネイティブ用に`where codex`相当または`std::fs`による直接ファイル存在確認を実装。パス形式もWindowsパス（`C:\...\codex.cmd`等）に |
| プロジェクトフォルダ選択 | `windows_path_to_wsl`でWSL UNCパスへ変換 | ネイティブ時は変換不要、選択したWindowsパスをそのまま使う（むしろ単純化） |
| ターミナル起動 | `open_wsl_terminal`がWSL端末を開く | ネイティブ用に`cmd.exe`/`powershell.exe`をそのフォルダで起動する別実装が必要 |
