### Ver.1.1以降へ延期可能

#### `-32001`(Server overloaded)の安全な自動再試行

現状でもエラー表示はできるため機能は壊れておらず、再試行の実装ミスは二重実行の危険を伴う。急いで実装する理由が無いと判断し延期。

前提として、`RpcFailure`へJSON-RPCのcode/dataを保持できるようにする必要がある(現状は`server_rejected`がエラー全体を文字列化しているだけで、`message`の文字列検索で`-32001`を判定するのは不安全)。

```rust
pub struct RpcFailure {
    pub kind: RpcFailureKind,
    pub message: String,
    pub code: Option<i64>,
    pub data: Option<serde_json::Value>,
}
```

再試行してよいRPCは許可リスト(ブロックリストではない)で管理する。`thread/list`・`thread/read`・`model/list`・`account/rateLimits/read`は対象、`thread/start`・`turn/start`・承認応答・`thread/name/set`は対象外(二重実行につながるため)。

#### MCPサーバーのelicitation（対話的入力要求）への対応検討（2026-07-29発見）

ユーザーがサーバー診断ログ（`codex:stderr`）で発見。ANSIエスケープコード除去（0.5.8）で読みやすくなったログに、以下のエラーが2件記録されていた:

```text
2026-07-29T11:00:52.126559Z ERROR codex_app_server::message_processor: <- error: JSONRPCError { error: JSONRPCErrorError { code: -32601, data: None, message: "Unsupported server request method: mcpServer/elicitation/request" }, id: Integer(0) }
2026-07-29T11:00:52.130420Z ERROR codex_app_server::bespoke_event_handling: request failed with client error: JSONRPCErrorError { code: -32601, data: None, message: "Unsupported server request method: mcpServer/elicitation/request" }
```

原因調査の結果、これはWslCodexGui側の設計通りの挙動と判明した。[approvalMethods.ts](../app/src/approvalMethods.ts)の`APPROVAL_METHODS`は承認系4種類（`item/commandExecution/requestApproval`・`item/fileChange/requestApproval`・`execCommandApproval`・`applyPatchApproval`）のみを認識し、それ以外のserver requestは`App.tsx`のイベントハンドラが`reject_server_request`で機械的に`-32601`エラーを返す（未対応method発生時に無応答で固まるより、明確に失敗を返す方針。既存の設計判断を踏襲）。

`mcpServer/elicitation/request`は、接続中のMCPサーバーがユーザーへ対話的な追加入力を求める際に使われるリクエストと推測される（未確認）。現状は問答無用で拒否しているため、**elicitationを使うMCPサーバーの機能はWslCodexGuiでは使用できない**。

**未対応・検討事項**:
- どのMCPサーバー・どの操作がこのelicitationを発行しようとしたか（ログのみでは特定できず、ユーザー環境の`~/.codex/config.toml`の`mcp_servers`設定と突き合わせる必要がある）
- `mcpServer/elicitation/request`の実際のパラメータ形状（`generate-json-schema`で確認可能。未実施）
- 対応する場合、承認UIと同様の動的フォームが必要になる可能性が高く、実装コストは承認UIより高いと見込まれる
- 現時点でユーザーの実作業に支障が出ているか未確認のため、優先度判断は保留

**候補の絞り込み（2026-07-29、実機確認）**: ユーザー環境（WSL Ubuntu-20.04）の`~/.codex/config.toml`を確認したところ、`[mcp_servers.*]`セクションは存在しなかったが、代わりに以下の`[plugins."<name>@openai-curated"]`が有効化されていた:

これらは内部的にMCPサーバーとして実装されている可能性が高く、`mcpServer/elicitation/request`（ログの11:00:52台）はこの4つのいずれかが発行したものと推測される（未確定。ログのタイムスタンプと、その時刻に実行していたスレッドの内容を突き合わせる必要がある）。

#### `codex_models_manager`のモデル一覧更新タイムアウト（2026-07-30発見、事実記録のみ）

ユーザーがサーバー診断ログ（HAYABUSAプロジェクト、WSL Ubuntu-20.04接続）で発見:

```text
2026-07-30T04:19:28.835244Z ERROR codex_models_manager::manager: failed to refresh available models: timeout waiting for child process to exit
```

「利用可能なモデル一覧」を更新する処理が、何らかの子プロセスの終了待ちでタイムアウトしたというCodex内部のエラー。WslCodexGui側は`model/list`RPCを送るだけで、この「子プロセス」を自ら起動する箇所を持たない（[App.tsx](../app/src/App.tsx)の`openModelPicker`/`fetchDefaultModel`はいずれも`rpc_request`経由の単純なJSON-RPC呼び出し）ため、WSL内のcodex CLI自体の内部実装（`codex_models_manager`が何らかの外部コマンドを呼んで最新モデル一覧を取得している可能性）に起因すると推測される。

このエラー発生時もフッターの接続状態は"Codex server connected (owned)"のまま維持されており、既存の接続・スレッド操作への影響は確認されていない（実害はモデル一覧の更新失敗のみと推測、未確認）。「子プロセス」の正体を含め原因調査に必要な材料が手元にないため、現時点では深追いせず事実の記録に留める。再発時に頻度・実害（フッターの🧠モデル一覧が古いまま更新されない等）が確認できれば、優先度を見直す。

```
exitCode: 0, 出力: hello-from-native-windows-codex
```

分かった注意点:

- **`.cmd`ファイルのspawn**: Node.jsの`child_process.spawn()`で`codex.cmd`を直接渡すと`EINVAL`になり`shell: true`が必要だった。Rust（`std::process::Command`）でも同様の配慮が要る（`cmd.exe /c`経由にする、または拡張子なしの`codex`シムを使う等、実装時に要検証）。
- **コマンド実行系統がWSL版と異なる**: WSL版は`bash -lc '...'`、ネイティブ版は`pwsh.exe -Command '...'`で実行される。承認モーダルのコマンド表示欄など、ユーザーに見せる文字列の見た目が変わる。
- **軽微なstderr警告**: `failed to load models cache: missing field 'supports_reasoning_summaries'`が出たが動作に支障はなかった（Windows側0.144.6とWSL側0.145.0のバージョン差によるモデルキャッシュ形式の非互換と推測、実害なし）。
- 承認レベル・サンドボックス設定など、既存の`thread/start`パラメータはネイティブ側でも同様に機能した。

##### アーキテクチャ方針

`rpc_request`／`respond_server_request`／`reject_server_request`（[lib.rs](../app/src-tauri/src/lib.rs)）はプロセスの起動方法を一切知らない、プロトコル層として独立している。プロセス起動を担う唯一の箇所は[`Connection::spawn`](../app/src-tauri/src/appserver.rs)内の

```rust
let mut cmd = Command::new("wsl.exe");
cmd.args(["-d", distro, "--exec", codex_path, "app-server"]);
```

のみであり、ここを接続方式で分岐させれば、以降のRPCハンドリングは無改造で流用できる。既存のWSLフローを壊さないよう、**「接続方式（WSL／Windows-native）」を明確に分けたトグルとして追加し、内部処理も分岐させる**方針とする（1つのコードパスに無理に統合しない）。

無操作の判定は**デスクトップ全体**が条件なので、WebViewのイベント（自ウィンドウに配送された入力しか見えない）では実装できない。Win32の`GetLastInputInfo`がセッション全体の最終入力時刻を返すため、これを読む`system_idle_millis`コマンドをRust側に追加した（`windows-sys`をWindows限定の依存として追加、`Win32_Foundation`/`Win32_System_SystemInformation`/`Win32_UI_Input_KeyboardAndMouse`）。OSが元々持っているカウンタを読むだけで、フックは仕掛けておらず、キーの内容もカーソル座標も一切観測しない。`GetTickCount`との差分は`wrapping_sub`で取り、約49.7日でのカウンタ一周をまたいでも正しい値になる。非Windowsビルドでは0（=直前に操作あり）を返し、通知が誤発火せず単に無効になるようにした。

既知の制約: `requestUserAttention`はTauriのAPIドキュメント通り**アプリが既にフォーカスされている場合は無効**。離席時にこのアプリを最前面にしたまま離れると点滅しない。OS側の挙動（アクティブなウィンドウは点滅させない）でもあるため、現時点では受け入れる。

**日本語入力の重さと、スクロールの強制追従（2026-08-10、0.5.21）**: ユーザーから「日本語入力がプロンプト欄に入らずデスクトップ左上に弾かれて表示される」「AIが動作していない時でも日本語への反応が鈍い。常にではなくスレッドによる。むらがある」との報告。あわせて「AIが動作中にスクロールして過去の出力を見ていると、新しい出力で最新へ戻されてしまう。ユーザーが触っていない時だけ追従してほしい」との要望。

**「スレッドによる」が決め手だった。** 実データを測ったところ、常用スレッドが桁外れに巨大だった。

| スレッド | サイズ | 行数 |
| --- | --- | --- |
| `019fcc86-8c0a-7d21` | 79MB | 40,503 |
| `019fbb5e-fe8a-7c30` | 57MB | 21,243 |
| 3位以下 | 13〜22MB | 5,000〜8,600 |

最大のスレッドの内訳は reasoning 6,865件、custom_tool_call とその出力 11,320件、function_call とその出力 2,914件、message 1,014件で、**描画対象がおよそ2万件**に達する。上位2つは実際にユーザーが日常的に使っているスレッドである（503エラーの報告に出ていたものと、フッターに表示されていたもの）。

原因は打鍵ごとの再描画コスト。`input`はAppのstateなので1文字ごとにApp全体が再描画され、`items.map()`が2万個のReact要素を作り直していた。`TranscriptItem`の`memo`化は既に入っていた（前セッションの対策。コメントに「IME入力ラグの主因」と明記）が、これは各要素の**中身**の再描画を防ぐだけで、要素生成と差分照合そのものは毎打鍵で走っていた。加えて2万件規模のDOMではブラウザ側のレイアウト計算とIMEのキャレット位置解決も重くなり、仕様書[N-05](仕様書.md)(c)「変換候補ウィンドウの表示位置がテキスト入力欄に追従する」が破綻していたと考えられる。

対策3点:

1. **`items.map()`を`useMemo`で包んだ**。配列の同一性が保たれるため、Reactはトランスクリプト部分木の照合を丸ごと省略する。打鍵ごとの2万件分の要素生成が消える。

**なお、連続するアシスタント発言を1つの吹き出しにまとめる案はユーザーの判断で却下された**（2026-08-10）。理由は「事実を改変するのはよくない」。codexが2件の発言として生成したものを1件に見せれば、**「2回発言した」という事実そのものが表示から消える**。

判断基準は**見栄えと、内容およびその意味を分けて考える**こと（ユーザーの整理）。

| 区分 | 可否 | 例 |
| --- | --- | --- |
| 内容・意味を変える | **不可** | 発言の統合・省略・要約・並べ替え |
| 見栄えだけを変える | 可 | 色、余白、字体、境界線の引き方、役割接頭辞の視覚的区別、折りたたみ（展開すれば全文が見える） |

読みやすさのための調整自体は歓迎される。禁じられるのは、**記録が語っている事実が読み取れなくなる**変更である。

ユーザーによる具体例（2026-08-10）: 文字色やサイズのような見栄えはその都度判断してよいが、**メッセージの事実部分は保存する**。上記の2度繰り返すケースであれば、**2件目を畳んで「（同一メッセージ有）」等と示すのは可**。畳んでも「2件あった」という事実は残り、展開すれば全文が読めるため。統合が不可なのは件数そのものが消えるからである。

**メッセージの折りたたみ（2026-08-10、0.5.28）**: 「1回の入力に2回答える」件（上記）を受けての表示改善。ユーザーの判断は「2件目を畳んで『（同一メッセージ有）』等と示すのは可」。

**ただし「同一かどうか」の自動判定は行わない**。観測された2件を実測したところ:

| | 1件目 | 2件目 |
| --- | --- | --- |
| 文字数 | 208 | 106 |
| 完全一致 | 否 |
| 類似度 | **0.503** |

2件目は言い直した短縮版であり逐語的な繰り返しではない。したがって完全一致判定では**このケース自体が引っかからず**、類似度0.5前後で畳む設定にすると**話題が同じで内容の違う発言まで畳む**。「同じ意味だ」と判断することは意味の解釈であり、[見栄えと内容・意味を分ける](#その他)方針に照らせば表示層の仕事ではない。

採用したのは**判定せず、すべてのメッセージを手動で折りたためるようにする**方式（ユーザー承認済み）。畳むかどうかは常に人が決める。

- ホバーでコピーボタンの左に▼が出る。畳むと1行の要約と▶が残り、要約行のクリックで展開する。
- 畳んでも枠と要約は残るため「そこに発言があった」事実は消えない。展開すれば全文が戻る。
- **畳んだ状態はセッション内のみ**。これは読み手の位置であって会話の属性ではなく、保存すると次回起動時に最初から隠れているメッセージが生まれる。それは事実の隠蔽に近い。
- 畳んでいる間は▼を常時表示（戻る手段がそれしかないため）。
- 対象はコピー可能なメッセージすべて。種類を限る理由がない。

要約行の抽出は[collapsePreview.ts](../app/src/collapsePreview.ts)。

**承認ダイアログの表示時刻と、経過時間の一時停止（2026-08-10、0.5.28）**: ユーザーから「ダイアログを出した時刻を隅に小さく表示。ダイアログが出ている間は継続時間のカウントアップを止める」との要望。

- **到着時刻をモーダル右上に表示**。記録は**要求が届いた瞬間**であり描画時ではない。離席中にダイアログが出ていた場合、意味があるのは「codexがいつ聞いてきたか」であって「いつ画面に出たか」ではない。
- **承認待ちの間は経過時間を停止**。経過時間は「AIがどれだけ働いたか」を答えるものであり、承認ダイアログはまさに**AIが止まって人を待っている**状態である。含めるとダイアログを開いたまま10分離席しただけでターンが10分長くかかったように見える。

計算は[turnClock.ts](../app/src/turnClock.ts)へ切り出した。**一時停止は開始時刻を後ろへずらす**方式で、経過時間はどこでも単なる`now - start`のままとなり、別途「停止時間の累計」を持たずに済む（同期ずれの余地が無い）。テストで待機中に数字が進まないこと、複数回の承認それぞれの待ち時間が差し引かれること、二重停止で二重計上されないこと、**システム時刻が巻き戻ってもターンが短く見えない**ことを検証している。

`tsc --noEmit`・`npm run build`・`npm test`（**99件**、`collapsePreview.test.mjs` 7件と`turnClock.test.mjs` 8件を追加）に合格。

```text
Ollama: 172.21.112.1:11434
画面のモデル一覧: http://172.21.112.1:11434/api/tags → 成功
Codex実行時: http://172.21.112.1:11434/responses → 404 Not Found
```

- `ollamaBaseUrl`をGUI入力欄・`localStorage`保存値として追加
- Windows側の`OLLAMA_HOST`を初期値へ変換し、未設定時は`http://127.0.0.1:11434`を使用
- `/api/tags`のモデル一覧取得と、Codex用`/v1` endpointを分離

> 自分のウィンドウにフォーカスがないとき、フォーカスが戻るまで点滅する、をORで付け加えてほしい。マウスを動かしても他のウィンドウの下に隠れていると点滅が止まってしまい気付かないことがある。

原因は、従来の実装が「デスクトップのどこかで入力があったら即座に点滅を止める」という判定だったため、WslCodexGuiのウィンドウが他のウィンドウの下に隠れて非フォーカスのまま、別のウィンドウでマウス操作をしただけで点滅が止まってしまうことだった。

- **停止条件**: 「どこであれ入力を検知したら停止」から「**このウィンドウにフォーカスが戻っており、かつ**入力を検知したら停止」へ変更（`shouldStopFlashing`）。フォーカスが他のウィンドウにある間は、どれだけそちらで操作しても点滅を止めない。なお、フォーカスが実際にこのウィンドウへ戻る操作（クリックやAlt+Tab）自体も「入力」に該当するため、フォーカスが戻った直後のポーリング（500ms以内）で自然にこの条件を満たし、素早く反応する。
