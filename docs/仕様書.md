## 1. 背景と目的

### 1.1 背景

- Windows GUI版 Codex アプリは、動作が不安定・機能不足であり、実用上の不満が大きい。
- 一方、WSL2 上で動く Codex CLI（Linux版）は安定して動作するが、ターミナル（TUI）操作に限定される。
- Codex には VS Code 拡張などのリッチクライアント向けに `app-server` という公式インターフェースが提供されており、認証・会話履歴・承認要求・ストリーミングイベントを構造化された形で扱える。

### 1.2 目的

WSL2 上で動作する `codex app-server` を実行系（バックエンド）とし、Windows ネイティブの GUI をフロントエンドとする専用クライアントを構築する。これにより、

- Windows版公式アプリの不安定さを回避する
- ターミナル出力の画面解析（ANSIパース等）を避け、構造化イベントベースの安定したGUIを実現する
- Codex の実行環境（認証情報・設定・ツールチェーン・Linux sandbox）はすべてWSL側に閉じ込め、Windows側は表示・入力に専念する

### 1.3 非目的（スコープ外）

- Windows版公式Codexアプリの機能を全て再現すること（MVPでは最小機能に絞る）
- リモート／外部ネットワークからの接続対応（localhost限定とする）
- Windows ネイティブ実行のCodex（WSLを介さない実行）のサポート

| codex app-server proxy | 指定したUnixソケットへ1本の生ストリーム接続を開き、そのソケットとstdin/stdoutの間でバイトを中継する公式サブコマンド |
| WSL2 | Windows Subsystem for Linux 2。Windows上でLinuxカーネルを動かす仕組み |
| ラッパーGUI（本アプリ） | 本仕様書で構築するWindowsネイティブGUIアプリケーション |
| sandbox | Codexがコマンド実行やファイル変更を行う際の権限モード（例: workspace-write） |
| プロセス所有権（owned/attached/external） | 本アプリが接続したapp-serverプロセスを自ら起動したのか、既存のプロセスに接続しただけなのかを区別する状態。詳細は[4.2節N-14](#42-非機能要件) |
| localhostForwarding | WSL2の既定機能。WSL内のlocalhostポートをWindowsホストからも接続可能にする（代替構成でのみ関係する） |

## 3. 全体構成

主構成は、Windows GUI（Tauri Rustバックエンド）が`wsl.exe`を子プロセスとして起動し、その標準入出力パイプを`codex app-server`（stdio既定モード）に直結する方式とする。**ネットワークポートを一切使用しない。**

```text
┌──────────────────────────────┐
│ Windows GUI（本アプリ）        │
│ Tauri 2 + React/TypeScript   │
│ Rustバックエンド               │
│                              │
│ ・チャットUI                 │
│ ・差分表示（Monaco Diff）     │
│ ・承認ボタン                 │
│ ・プロジェクト管理           │
└──────────────┬───────────────┘
               │ 子プロセスの stdin/stdout（パイプ、ポートなし）
               ▼
   wsl.exe -d <ディストリ名> --exec codex app-server --listen stdio://
               │ JSONL（改行区切りJSON）
               ▼
┌──────────────────────────────┐
│ WSL2（Ubuntu等）              │
│ codex app-server（stdio既定モード）│
│                              │
│ ・Linux版Codex CLI            │
│ ・Linux sandbox               │
│ ・git / node / python 等      │
│ ・WSL内プロジェクトファイル    │
└──────────────────────────────┘
```

- Windows側はUIレンダリングと入力、および`wsl.exe`子プロセスの起動・パイプ通信のみを担当する。
- Codex本体・設定・認証情報・ツールチェーン・プロジェクトファイルはすべてWSL側に置く。
- **主構成ではリスニングポートを開かない。** そのためポート競合・なりすまし接続・WebSocket固有の実験的機能リスクといった問題が構造的に発生しない。
- WebSocketやUnixソケットを使う構成は、主構成で要件を満たせない場合の代替構成として[5.4節](#54-代替構成優先順位付き)に位置づける。

## 4. 要件定義

### 4.1 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| F-01 | GUI起動時、Rustバックエンドが`wsl.exe`を子プロセスとして起動し、その標準入出力を`codex app-server`（stdio既定モード）へ直結する。ネットワークポートへの接続処理は行わない（主構成） | 必須 |
| F-02 | WSL内のプロジェクト（パス）を一覧・選択できる。最近使ったプロジェクトを保存する | 必須 |
| F-03 | チャット形式でユーザーメッセージ／アシスタント応答／reasoning状態／コマンド実行内容／実行結果／ファイル変更／承認要求／エラーを表示する | 必須 |
| F-04 | Codexがコマンド実行やファイル変更の承認を求めた際、GUI上で選択肢を提示して応答できる。各承認要求はapp-serverが発行する一意なrequest IDで管理し、二重応答を防止する。ボタンとapp-serverの承認レスポンス値との対応関係、および「拒否」（対象操作のみ拒否してturn継続）と「中止」（turn全体を停止）の違いを明確に区別する（詳細は[7.3節](#73-承認ui)） | 必須 |

| F-05b | undoを実装する場合（フェーズ3以降）、各turn開始時のファイル内容とハッシュを保持し、現在のファイルハッシュが変更直後のハッシュと一致する場合に限り、そのturnが行った変更を復元できることとする | 任意（フェーズ3） |

| F-06b | app-serverプロセスの強制終了は確認ダイアログを伴う管理操作とし、通常のStop操作とは明確に分離する | 必須 |

| F-08a | 通信異常またはapp-server子プロセスの異常終了を検知した場合、新しいapp-serverプロセスを起動し直せる | 必須 |
| F-08b | GUIまたはapp-server再起動後、保存済みthread一覧を取得し、対象threadを選択して会話を再開できる（thread本体はCodex側を正本とする。[8.1節](#81-データ保存方針gui側-vs-codex側)参照） | 必須 |

### 4.2 非機能要件

| ID | 要件 |
|---|---|
| N-01 | 主構成（stdio直結）ではネットワークポートを一切開かない。WebSocket／Unixソケットの代替構成を採用する場合のみ`127.0.0.1`限定でバインドし、外部（`0.0.0.0`）には公開しない |
| N-02 | OpenAI／ChatGPT認証情報はWindows GUI側に一切保持・表示しない。認証はWSL内のCodexに一任する。代替構成でWebSocketを使う場合にのみ必要となるローカル通信用capability tokenは、OpenAI認証情報とは別個の秘密として扱ってよい（[N-11](#42-非機能要件)参照） |
| N-03 | `wsl --shutdown` のような、他のWSLプロセス（Docker等）にも影響する破壊的操作は行わない。終了対象は自らが起動した（owned）プロセスに限定する（[N-14](#42-非機能要件)） |
| N-04 | プロジェクトファイルはWSL側のLinuxファイルシステム（例: `~/src/...`）に置くことを前提とし、`/mnt/c/...`経由のWindowsファイルシステムアクセスは推奨しない |
| N-05 | GUIは日本語IME入力に対応する。具体的には: (a) IME変換確定前のEnterキー入力でメッセージを誤送信しない、(b) IME変換中のEscでの変換取り消しがテキスト入力欄の他の挙動と競合しない、(c) 変換候補ウィンドウの表示位置がテキスト入力欄に追従する |
| N-06 | 通信異常・app-server異常終了時にGUIがクラッシュせず、再接続や再起動を案内する。stdio直結時は子プロセスのexit codeとstderr内容から異常終了理由を判別する |
| N-07 | 動作対象とするCodex CLIの最小バージョンを明記し、起動時にバージョン不一致を検知した場合はユーザーに警告する。**現時点で最小バージョンは未確定（TBD）**。フェーズ1のPoC（[10節](#10-実装フェーズ)）で動作確認したバージョンを確定させ、本行を具体的なバージョン番号で更新すること |
| N-08 | ログ・会話履歴のローカル保存には保持上限（サイズまたは期間）を設け、無制限に肥大化させない |
| N-09 | 会話履歴・ログにはプロジェクトのコード内容が含まれ得るため、保存先はクラウド同期対象外のディレクトリ（例: `AppData\Local`）に限定し、OneDrive等の同期フォルダには置かない |
| N-10 | プロトコル互換性の判定はバージョン番号比較だけに頼らない。対応Codex CLIバージョンから`codex app-server generate-ts`（またはJSON Schemaが必要な場合は`generate-json-schema`）で生成したスキーマをビルド時にリポジトリへ組み込み、受信メッセージを境界でランタイム検証する。未知のnotification methodは無視してログへ残すのみとし、GUI全体は停止させない。必須メソッド・必須フィールドの不一致がある場合に限り「非対応」として扱う |
| N-11 | 代替構成でWebSocketトランスポートを使用する場合、`--ws-auth capability-token`を必須とする |
| N-12 | 上記capability tokenはOpenAI認証情報とは別のローカル通信資格情報として扱い、Windows Credential Manager等で保持してよい |
| N-13 | capability tokenはコマンドライン引数へ直接渡さず`--ws-token-file`を使用する。トークンファイルの権限はWSL側で0600とする |
| N-14 | 本アプリが自ら起動した（owned）app-serverプロセスのみを終了対象とする。既存プロセスへ接続（attached）した場合、そのプロセスを終了しない。主構成（stdio直結）ではGUIが子プロセスを直接spawnするため、常にownedとなる |
| N-15 | 接続成立後は`initialize`を実行し、app-serverであること・CLIバージョン・プロトコル互換性を確認してから利用可能状態へ移行する。代替構成でWebSocketを使う場合は接続前に`/readyz`を確認する |
| N-16 | JSON-RPCエラー`-32001`（Server overloaded; retry later.）は再試行可能エラーとして扱い、指数バックオフとジッターを用いて再試行する |
| N-17 | 同一threadへのturn開始要求はクライアント側で直列化し、二重実行を避ける |
| N-18 | 大量のdelta通知を1件ずつUI状態へ反映せず、16〜50ms程度の単位でバッチ更新する |
| N-19 | 子プロセス（wsl.exe / app-server）のstdoutとstderrは、起動直後から専用タスクで継続的に読み出し続ける。読み出しを怠るとOSパイプバッファが満杯になりプロセスがブロックしうる |

## 5. アーキテクチャ設計

### 5.1 通信方式（主構成: stdio直結）

- Windows GUI（Tauri Rustバックエンド）は`wsl.exe`を子プロセスとして起動し、その標準入力・標準出力を直接パイプ接続する。ネットワークポートは使用しない。
- 起動コマンド例: `wsl.exe -d <ディストリ名> --exec codex app-server --listen stdio://`
  - `--exec`（`-e`）はWSLの既定ログインシェルを介さず直接コマンドを実行するオプション。
  - 引数はシェルを介さず配列で渡し、`bash -lc`やシェルスクリプト経由を避けることで、引用符問題とシェルインジェクションのリスクを減らす。
- 通信フォーマットはJSONL（改行区切りJSON、JSON-RPCに準じた形式）。これはapp-serverの既定・最も実績のあるトランスポートである。
- 受信する構造化イベントの種類は変わらない: 会話メッセージ（ユーザー／アシスタント）、reasoning状態、コマンド実行要求・実行結果、ファイル変更（diff）、承認要求、エラー。

> **この構成を主構成とする理由**
> - WebSocketトランスポート（`--listen ws://`）は公式に「experimental and unsupported」と明記されている一方、stdioは既定・最も実績のある経路である。
> - リスニングポートが存在しないため、ポート管理・ポート競合・なりすまし接続・WSLネットワーク設定差異・Origin/HTTP Upgrade処理・WebSocket認証といった懸念事項が構造的に発生しない。
> - `wsl.exe`の子プロセスとしてGUIが直接所有するため、プロセス所有権（[N-14](#42-非機能要件)）が自明になる。

> **既知の未確認事項（要PoC検証）**
> - `wsl.exe --exec`を用いた場合の正確な引数の渡し方・エスケープ挙動（PoCで実機確認する）。
> - stdio直結時、GUI（親プロセス）が異常終了した場合に子プロセス（wsl.exe / app-server）が孤児として残らないか。
> - GUI再起動のたびにapp-serverを起動し直す設計となるため、[F-08b](#41-機能要件)「thread再開」はCodex側のthread永続化・resume機能に依存する。実際に機能するかをPoCで確認する（[10節](#10-実装フェーズ)P0項目）。

### 5.2 プロセス起動フロー（主構成）

```text
1. Rustバックエンドが wsl.exe を子プロセスとしてspawnし、stdin/stdoutをパイプで取得する
   wsl.exe -d <ディストリ名> --exec codex app-server --listen stdio://
2. 起動直後からstdout/stderrを別タスクで継続的に読み出し開始（N-19）
3. initializeリクエストを送信し、応答からapp-serverであること・バージョンを確認する（N-15）
4. 保存済みthread一覧を取得する
5. プロジェクト／threadを開く（新規作成 または 既存threadのresume）
```

推奨実装（Tauri Rust側）:

```rust
use std::process::{Command, Stdio};

let child = Command::new("wsl.exe")
    .args([
        "-d", "Ubuntu",
        "--exec", "codex", "app-server", "--listen", "stdio://",
    ])
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped())
    .spawn()?;

// stdout / stderr は起動直後から別タスクで継続的にドレインすること（N-19）。
// 放置するとOSパイプバッファが満杯になり子プロセスがブロックする。
```

- ディストリ名は設定ファイル（`settings.json`）で指定可能にする（既定値のハードコーディングを避ける）。
- `-d`と`--exec`の順序・構文はWSLのバージョンによって挙動が変わりうるため、PoCで実機確認する。

### 5.3 終了フロー（主構成）

- GUI終了時、子プロセス（wsl.exe / app-server）へ標準入力のクローズ（EOF）またはプロセス終了シグナルを送り、確実に終了させる。
- GUIが異常終了（クラッシュ）した場合に子プロセスが孤児として残らないか、PoCで確認する（[10節](#10-実装フェーズ)）。必要であればWindows Job Object等で子プロセスのライフタイムを親プロセスに紐づけることを検討する。
- 主構成では「GUIを閉じてもサーバーを残す」設計は採用しない（[F-13](#41-機能要件)は主構成では対象外）。サーバー永続化が必要な場合は[5.4節](#54-代替構成優先順位付き)の代替構成を検討する。
- いずれの構成でも `wsl --shutdown` は使用しない（他プロセスへの影響を避けるため）。

### 5.4 代替構成（優先順位付き）

主構成（stdio直結）で致命的な問題（例: thread resumeが機能しない、孤児プロセス問題が解決できない、複数クライアントからの同時接続が必要になった等）が判明した場合に限り、以下を優先順位順に検討する。

**A. 公式Unix socketトランスポート + `codex app-server proxy`（優先）**

公式README記載の機能:
- `--listen unix://` または `--listen unix://PATH`: Unixドメインソケット上で標準HTTP UpgradeによるWebSocket接続を提供する
- `codex app-server proxy`: 指定したUnixソケット（既定は`$CODEX_HOME/app-server-control/app-server-control.sock`）へ1本の生ストリーム接続を開き、そのソケットとstdin/stdoutの間でバイトを中継する公式サブコマンド

```text
Windows GUI
    │ stdin/stdout（wsl.exe子プロセス経由、主構成と同じ実装）
    ▼
wsl.exe -d <distro> --exec codex app-server proxy
    │ Unixドメインソケット
    ▼
codex app-server --listen unix://（WSL内で常駐）
```

- app-server本体をWSL内で常駐させつつ、Windows側の実装は主構成（5.1〜5.3）とほぼ同じstdioパイプ処理のままで、サーバー永続化（[F-13](#41-機能要件)相当）を実現できる可能性がある。
- 自作コードが不要で、公式サポート範囲内の機能のみで完結する点が最大の利点。ただし`proxy`・Unixソケット経路自体の安定性は別途PoCで確認が必要。

**B. 自作ブリッジ（Aで要件を満たせない場合のみ）**

```text
Windows GUI
    │ TCP / WebSocket（自作プロトコル）
    ▼
WSL2内の自作中継プロセス（Node.js等・軽量）
    │ stdio（JSONL）
    ▼
codex app-server（stdio既定モード・常駐）
```

- 中継プロセスはWindows GUI側の接続が切れても終了させずWSL内で生かし続け、app-serverとのstdio接続を維持できる。
- デメリットは自作の中継プロセスがもう一つの保守対象になる点（プロセス監視・異常終了時の再起動ロジックを自前で持つ必要がある）。公式のUnix socket + proxy（A）で要件を満たせないことが確認された場合のみ採用する。

**C. `--listen ws://`（開発・検証用途に限定）**

- 公式に「experimental and unsupported」と明記されているため、常用構成としては採用しない。PoCでのデバッグや、ブラウザ製デバッグツールからの一時的な接続確認等の用途に限定する。
- 採用する場合は[N-11〜N-13](#42-非機能要件)（capability tokenによる認証必須化）を満たすこと。

**採用判断はいずれもフェーズ1のPoC結果を踏まえて行う**（[10節](#10-実装フェーズ)参照）。

## 6. 技術選定

### 6.1 第一候補: Tauri 2 + React/TypeScript

| 項目 | 内容 |
|---|---|
| フロントエンド | React + TypeScript |
| デスクトップフレームワーク | Tauri 2 |
| エディタ／差分表示 | Monaco Editor / Monaco Diff Editor |

選定理由:
- 軽量で、子プロセス管理やJSON構造の表示を実装しやすい。
- Monaco Editorをそのまま利用でき、コード差分UIの実装コストが低い。
- Windows固有処理（`wsl.exe`の子プロセス起動・パイプ管理）はRust側で担当（[5.2節](#52-プロセス起動フロー主構成)のコード例を参照）。

### 6.2 第二候補: WPF / WinUI 3 + C#

| 項目 | 内容 |
|---|---|
| UI | WPF または WinUI 3 |
| ランタイム | .NET |
| 通信（主構成） | `System.Diagnostics.Process`の標準入出力パイプ |
| エディタ | WebView2 + Monaco Editor |
| ストレージ | SQLite |

選定理由:
- タスクトレイ、通知、ジャンプリスト、Windows資格情報マネージャー、プロセス監視などのWindows統合機能を実装しやすい。

### 6.3 選定方針

- UI開発速度・実装コストを優先する場合: **Tauri 2案を採用**。
- Windows OS機能との統合（通知・タスクトレイ等）を優先する場合: WPF/WinUI 3案を検討。
- 本仕様書ではMVP実現速度を優先し、**Tauri 2 + React + TypeScript + Monaco Editor** を採用構成として確定する。

### 7.3 承認UI

```text

```

- ターミナルラッパー方式との最大の差別化ポイント。承認要求を構造化イベントとして受け取り、専用UIで提示する。
- 各承認要求は、app-serverが発行する一意なrequest ID（またはcall ID）を内部状態として保持する。
- 上記のボタンは、app-serverが受理する承認レスポンス値へ明示的に対応づける（マッピングの具体値はPoCでプロトコルを確認して確定する）。「今回だけ拒否」（対象操作のみ拒否してturnを継続する）と「中止」（turn全体を停止する）は意味が異なるため、混同しないよう明確に区別する。

- 通信が切断されている間、承認ボタンは無効化する。
- 承認待ちのままapp-serverが終了した場合は「失効」と表示する。

- Monaco Diff Editorを埋め込み、差分の視覚的レビューを可能にする。

- `(owned)`部分はプロセス所有権状態（owned/attached/external、[N-14](#42-非機能要件)）を表す。

## 8. ディレクトリ構成

```text
Windows側:
C:\Users\<user>\AppData\Local\WslCodexGui\
├── settings.json
├── projects.json
├── logs\
└── WslCodexGui.exe

WSL側:
~/.codex/
├── config.toml
└── ...

~/src/
├── project-a/
└── project-b/
```

方針:
- リポジトリは原則WSL側Linuxファイルシステム（`~/src/project`）に配置する。
- `/mnt/c/Users/.../project` のようなWindows側ファイルシステムへの配置は、ファイル監視・パーミッション・シンボリックリンク・Git挙動の面で問題が生じやすいため避ける。
- Windows側IDE／エクスプローラーからのアクセスが必要な場合は `\\wsl.localhost\Ubuntu\...` を利用する。
- 主構成（stdio直結）では起動スクリプト（`~/bin/start-codex-server`等）を経由しないため、WSL側の`~/bin/`は不要（[5.4節](#54-代替構成優先順位付き)の代替構成Bを採用する場合にのみ、中継プロセス用のスクリプト・実行ファイルをここに置く）。

### 8.1 データ保存方針（GUI側 vs Codex側）

会話履歴の二重管理を避けるため、正本の所在を明確にする。

| 種別 | 正本 | GUI側（SQLite）での扱い |
|---|---|---|
| 会話本文・turn・item・コマンド実行履歴・reasoningイベント | Codex側（app-server / thread） | 保存しない。表示のたびにapp-serverへ問い合わせる |
| 最近使ったプロジェクト、thread ID・表示名・最終アクセス時刻 | GUI側 | 表示補助データとして保存する |
| UI設定・ウィンドウ状態・お気に入り | GUI側 | 保存する |
| 接続したapp-serverのバージョン情報 | GUI側 | 保存する（互換性チェック用、[N-10](#42-非機能要件)） |

GUI側で会話本文を複製・キャッシュすると、Codex側履歴との不整合、イベント取りこぼし、同一threadの二重登録、Codex CLI更新後のデータ形式差、コード内容の保存範囲拡大といった問題が生じる。オフライン表示を要件にする段階になって初めて、キャッシュの追加を検討する。

## 9. セキュリティ仕様

| 項目 | 方針 |
|---|---|
| 通信経路（主構成） | Windows GUIは`wsl.exe`の子プロセスを標準入出力パイプで直結する。ネットワークポートを一切開かないため、ポートスキャン・なりすまし接続・外部プロセスからの不正接続といった、リスニングソケット特有の攻撃面が構造的に存在しない |
| 認証情報の扱い | OpenAI APIキー・ChatGPT/Codex認証トークンはWindows GUI側に一切保持・表示しない。認証はWSL内のCodexに一任する |
| 破壊的操作の回避 | `wsl --shutdown`等、対象アプリ以外のWSLプロセスに影響する操作は行わない。終了対象は自らが起動した（owned）プロセスに限定する（[N-14](#42-非機能要件)） |
| 代替構成採用時のバインドアドレス | `ws://127.0.0.1:PORT`に固定。`0.0.0.0`等の外部公開は行わない |
| 代替構成採用時の認証 | `--ws-auth capability-token`を必須とし、トークンは`--ws-token-file`で渡す（コマンドライン引数に直接渡さない）。トークンファイルの権限はWSL側で0600とする（[N-11〜N-13](#42-非機能要件)） |
| 代替構成採用時のOriginヘッダの扱い（要検証） | 公式ドキュメントは`/healthz`エンドポイントについて「Originヘッダを持つリクエストは403で拒否する」と明記しているが、これがWebSocketアップグレード処理そのものにも適用されるかは一次情報からは確認できていない。代替構成を採用する場合はPoCで実際の挙動を確認したうえで、ブラウザ等からの意図しない接続（drive-by接続）を防げるか判断する |
| ローカル保存データの扱い | 会話履歴・ログにはプロジェクトのコード内容が含まれ得るため、クラウド同期対象外のディレクトリに保存する（[N-09](#42-非機能要件)）。GUI側では会話本文を複製保存しない方針とする（[8.1節](#81-データ保存方針gui側-vs-codex側)）。第三者と共有するログ・スクリーンショットには機密コードが写り込んでいないか確認する |

## 10. 実装フェーズ

### フェーズ1: 動作確認（PoC）

まず主構成（stdio直結）の検証を行う。

```text
Windows Rust/Node.js クライアント
    │ 子プロセスstdin/stdout
    ▼
wsl.exe --exec codex app-server --listen stdio://
```

**P0: 実装方式決定に必要（★最優先）**
- ★ wsl.exe経由のstdio通信で、initializeからturn完了まで一連の流れが動作するか
- ★ stdoutにプロトコル（JSONL）以外の文字列が混入しないか
- ★ ログ・診断出力がstderrへ分離されているか
- ★ GUI終了時に子プロセス（wsl.exe / app-server）が確実に終了するか
- ★ GUI強制終了（クラッシュ）後に孤児プロセスが残らないか
- ★ 新しいapp-serverプロセスから、以前のプロセスが作成したthreadを一覧取得・resumeできるか（[F-08b](#41-機能要件)）
- ★ 実行中turnの最中にGUIを強制終了した場合、再起動後にそのturnの状態（完了／中断／状態不明）を判別できるか（[F-08c](#41-機能要件)）
- 使用するCodex CLIのバージョンを確認し、本仕様書の[N-07](#42-非機能要件)を確定値で更新する

**P1: プロトコル実装に必要**
- 承認要求中に接続が切れた場合の挙動
- Stop直後に到着する遅延イベントの扱い
- 同一threadへturnを連続送信した場合の挙動（直列化しない場合に何が起きるか、[N-17](#42-非機能要件)）
- `-32001`（Server overloaded）エラーの再現と、指数バックオフ＋ジッターでの再試行（[N-16](#42-非機能要件)）
- 未知のnotification methodを受けた場合の処理（無視してログに残すだけで済むか、[N-10](#42-非機能要件)）
- 非UTF-8または巨大なコマンド出力の扱い
- app-serverのstderrログ量が多い場合に、読み出しを怠るとデッドロックするか（[N-19](#42-非機能要件)）

**参考: 代替構成（[5.4節](#54-代替構成優先順位付き)）を評価する場合のみ追加で確認**
- Unix socket + `codex app-server proxy`経由でのサーバー永続化が機能するか
- `--listen ws://`使用時、想定していないOriginヘッダ（ブラウザ経由等）からの接続がどう扱われるか
- WebSocket採用時の`--ws-auth capability-token` / `--ws-token-file`の動作確認

上記P0項目で致命的な問題が判明した場合は、[5.4節](#54-代替構成優先順位付き)の代替構成への切り替えを検討する。

## 11. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 子プロセスの孤児化 | GUIクラッシュ時にwsl.exe/app-server子プロセスが残り続ける可能性 | PoCで検証（[10節](#10-実装フェーズ)P0）。必要であればWindows Job Object等でライフタイムを親プロセスに紐づける |
| stdout/stderr未分離によるデッドロック | 子プロセスの出力を読み出さないとOSパイプバッファが満杯になりプロセスが停止する | 起動直後から専用タスクで両方を継続的にドレインする（[N-19](#42-非機能要件)） |
| thread再開（resume）が機能しない可能性 | GUI/app-server再起動のたびに新規プロセスを起動する設計のため、Codex側のthread永続化・resume機能に依存する | PoCで最優先検証（[F-08b](#41-機能要件)）。機能しない場合は[5.4節](#54-代替構成優先順位付き)Aの常駐構成を検討する |
| 実行中turnの二重実行 | 切断・再接続時に同一リクエストを自動再送すると、コマンドやファイル変更が二重実行される恐れがある | リクエストの自動再送を禁止し、thread/turn状態を問い合わせてから判断する（[F-08c](#41-機能要件)、[N-17](#42-非機能要件)） |
| プロセス所有権の誤認 | 既存プロセスに接続した場合、それを自分のものと誤認し、終了操作で他用途のプロセスを巻き込む恐れ | owned/attached/externalの状態を明示的に管理し、終了操作はownedのみに限定する（[N-14](#42-非機能要件)）。主構成（stdio直結）ではGUIが子プロセスを直接spawnするため常にownedとなり、この問題は発生しない |
| UIパフォーマンス劣化 | トークンdeltaごとに逐次UI更新すると、長い応答や大量コマンド出力でUIが重くなる | 16〜50ms単位でのバッチ更新を行う（[N-18](#42-非機能要件)） |
| app-server過負荷時のエラー未処理 | リクエスト飽和時に返る`-32001`エラーを単純失敗として扱うと、再試行可能な状況で処理が止まる | 指数バックオフ＋ジッターでの再試行を実装する（[N-16](#42-非機能要件)） |
| app-serverのプロトコル変更 | Codexアップデートによりイベント仕様が変わる可能性 | 対応バージョンを固定し、そのバージョンから生成したスキーマ（`generate-ts`/`generate-json-schema`）をビルドに組み込み、ランタイム検証する（[N-10](#42-非機能要件)） |
| WSLディストリ名のハードコーディング | 環境によって既定ディストリ名が異なる | 設定ファイルでディストリ名を指定可能にする |
| 対応Codex CLIバージョンの未確定 | 現時点で本仕様が前提とする最小バージョンが未確定 | PoCで動作確認したバージョンを本仕様書に明記する（[N-07](#42-非機能要件)） |
| 会話ログの肥大化・情報漏洩 | ログにコード内容が含まれ、無制限に肥大化・クラウド同期される懸念 | 保持上限の設定（[N-08](#42-非機能要件)）、同期対象外ディレクトリへの保存（[N-09](#42-非機能要件)）、GUI側での会話本文の複製保存を避ける（[8.1節](#81-データ保存方針gui側-vs-codex側)） |
| **（代替構成採用時のみ）** WebSocketトランスポートが「experimental and unsupported」 | 公式README・ドキュメントに明記されている | 主構成（stdio直結）を採用する限り本リスクの影響を受けない。[5.4節](#54-代替構成優先順位付き)Cの用途を開発・検証用に限定する |
| **（代替構成採用時のみ）** ローカル無認証WebSocketへの意図しない接続 | ブラウザ等からの接続を完全には排除できない可能性がある（Originヘッダ検証の適用範囲は未確認、[9節](#9-セキュリティ仕様)） | capability token認証を必須化する（[N-11〜N-13](#42-非機能要件)） |
| **（代替構成採用時のみ）** app-server実装の未成熟さ（既知Issue） | GitHub Issue #19688（UDS-over-WebSocketハンドシェイク関連）など、既知の不具合報告が存在する | 実装開始前にopenai/codexのIssueトラッカーを確認する |
| WSL2ネットワーク設定の環境差異（代替構成採用時のみ） | `localhostForwarding`が無効化されている環境ではWebSocket/Unixソケット代替構成が使えない | 主構成（stdio直結）はこの問題の影響を受けない。代替構成採用時のみ起動時ヘルスチェックとドキュメント化で対応 |

```text
    │ stdin/stdout（パイプ、ネットワークポートなし）

wsl.exe --exec codex app-server --listen stdio://

認証:
OpenAI/ChatGPT認証情報はWSL内のCodexだけが保持する

会話履歴:
Codex側のthreadを正本とする。GUI側はthread参照情報のみ保存する

GUIローカル保存:
設定・プロジェクト一覧・thread参照情報・UI状態のみ

プロジェクト:
WSL Linuxファイルシステム（~/src/配下）

代替構成（優先順位順、必要な場合のみ）:
A. 公式Unix socket + codex app-server proxy
B. 自作ブリッジ（WSL常駐中継プロセス）
C. --listen ws://（開発・検証用途に限定。常用構成としては採用しない）
```

この構成により、Windows版Codexアプリの不安定なUI・実行環境切り替えに依存せず、安定したWSL版Codex CLIの実行系と使いやすいWindowsネイティブGUIを組み合わせた専用クライアントを実現する。

主構成をWebSocketからstdio直結へ切り替えたことで、WebSocketの実験的トランスポート、ポート競合、ローカル認証、WSLネットワーク設定差異、サーバー残存モデルといったリスクの大部分を設計段階で回避できる。残る中心的な課題はapp-serverプロトコル自体の実験的性質（stdio自体も含む）と、thread resumeの実動作であり、対応Codexバージョンの固定・生成スキーマによるランタイム検証・フェーズ1PoCでのthread再開確認によって管理可能な範囲に収める。
