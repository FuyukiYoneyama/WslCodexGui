## 1. 背景と目的

### 1.1 背景

- Windows GUI版 Codex アプリは、動作が不安定・機能不足であり、実用上の不満が大きい。
- 一方、WSL2 上で動く Codex CLI（Linux版）は安定して動作するが、ターミナル（TUI）操作に限定される。
- Codex には VS Code 拡張などのリッチクライアント向けに `app-server` という公式インターフェースが提供されており、認証・会話履歴・承認要求・ストリーミングイベントを構造化された形で扱える。

### 1.2 目的

WSL2 上で動作する `codex app-server` を実行系（バックエンド）とし、Windows ネイティブの GUI をフロントエンドとする専用クライアントを構築する。これにより、

- Windows版公式アプリの不安定さを回避する
- ターミナル出力の画面解析（ANSIパース等）を避け、構造化イベントベースの安定したGUIを実現する
- Codex の実行環境（認証情報・設定・ツールチェーン・Linux sandbox）はすべてWSL側に閉じ込め、Windows側は表示・入力に専念する

### 1.3 非目的（スコープ外）

- Windows版公式Codexアプリの機能を全て再現すること（MVPでは最小機能に絞る）
- リモート／外部ネットワークからの接続対応（localhost限定とする）
- Windows ネイティブ実行のCodex（WSLを介さない実行）のサポート

## 3. 全体構成

主構成は、Windows GUI（Tauri Rustバックエンド）が`wsl.exe`を子プロセスとして起動し、その標準入出力パイプを`codex app-server`（stdio既定モード）に直結する方式とする。**ネットワークポートを一切使用しない。**

```text
┌──────────────────────────────┐
│ Windows GUI（本アプリ）        │
│ Tauri 2 + React/TypeScript   │
│ Rustバックエンド               │
│                              │
│ ・チャットUI                 │
│ ・差分表示（Monaco Diff）     │
│ ・承認ボタン                 │
│ ・プロジェクト管理           │
└──────────────┬───────────────┘
               │ 子プロセスの stdin/stdout（パイプ、ポートなし）
               ▼
   wsl.exe -d <ディストリ名> --exec codex app-server --listen stdio://
               │ JSONL（改行区切りJSON）
               ▼
┌──────────────────────────────┐
│ WSL2（Ubuntu等）              │
│ codex app-server（stdio既定モード）│
│                              │
│ ・Linux版Codex CLI            │
│ ・Linux sandbox               │
│ ・git / node / python 等      │
│ ・WSL内プロジェクトファイル    │
└──────────────────────────────┘
```

- Windows側はUIレンダリングと入力、および`wsl.exe`子プロセスの起動・パイプ通信のみを担当する。
- Codex本体・設定・認証情報・ツールチェーン・プロジェクトファイルはすべてWSL側に置く。
- **主構成ではリスニングポートを開かない。** そのためポート競合・なりすまし接続・WebSocket固有の実験的機能リスクといった問題が構造的に発生しない。
- WebSocketやUnixソケットを使う構成は、主構成で要件を満たせない場合の代替構成として[5.4節](#54-代替構成優先順位付き)に位置づける。

## 4. 要件定義

### 4.1 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| F-01 | GUI起動時、Rustバックエンドが`wsl.exe`を子プロセスとして起動し、その標準入出力を`codex app-server`（stdio既定モード）へ直結する。ネットワークポートへの接続処理は行わない（主構成） | 必須 |
| F-02 | WSL内のプロジェクト（パス）を一覧・選択できる。最近使ったプロジェクトを保存する | 必須 |
| F-02a | プロジェクト一覧は、ユーザーが登録したパスと保存済みthreadの`cwd`（`thread/start`が受け付ける作業ディレクトリパラメータ）を基に構築する。WSLホーム以下の全体再帰探索は行わない | 必須 |
| F-02b | 自動探索を行う場合、設定された探索ルート（例: `~/src`、`~/work`）と最大深度に限定する | 推奨 |
| F-02c | プロジェクト選択時、WSL側で対象パスの存在・ディレクトリであること・アクセス可能性を検証する | 必須 |
| F-03 | チャット形式でユーザーメッセージ／アシスタント応答／reasoning状態／コマンド実行内容／実行結果／ファイル変更／承認要求／エラーを表示する | 必須 |
| F-04 | Codexがコマンド実行やファイル変更の承認を求めた際、GUI上で選択肢を提示して応答できる。**PoCで実機確認済み**（[10節](#10-実装フェーズ)）: 承認要求（`item/commandExecution/requestApproval`等）のパラメータには`availableDecisions`フィールドが含まれ、そのリクエストで実際に有効な決定肢（例: `"accept"`、`{"acceptWithExecpolicyAmendment":{...}}`、`"cancel"`。リクエストによっては`"acceptForSession"`/`"decline"`を含む場合もある）が動的に示される。GUIのボタンは固定3種類ではなく、この`availableDecisions`から動的に構築する。各承認要求はapp-serverが発行する一意なID（`ServerRequest`の`id`）で管理し、二重応答を防止する（詳細は[7.3節](#73-承認ui)） | 必須 |
| F-05 | ファイル差分をMonaco Diff Editorで表示できる | 必須 |
| F-05a | MVPでは差分表示のみとし、GUIからの一括undo機能は提供しない（対象範囲・Git管理外ファイル・新規/削除ファイルの扱いが未確定のため） | 必須（MVP方針） |
| F-05b | undoを実装する場合（フェーズ3以降）、各turn開始時のファイル内容とハッシュを保持し、現在のファイルハッシュが変更直後のハッシュと一致する場合に限り、そのturnが行った変更を復元できることとする | 任意（フェーズ3） |
| F-05c | undo実装時、競合（ユーザーによる別編集等）を検知した場合は自動復元せず、3-way diffを表示してユーザーに判断させる | 任意（フェーズ3） |
| F-06 | Stopボタンは現在実行中のturnへキャンセル要求を送るのみとし、app-serverプロセス自体は終了しない | 必須 |
| F-06a | 一定時間内にキャンセルが完了しない場合、「サーバーを再起動」操作を通常のStopとは別のボタンとして提示する | 推奨 |
| F-06b | app-serverプロセスの強制終了は確認ダイアログを伴う管理操作とし、通常のStop操作とは明確に分離する | 必須 |
| F-07 | 接続状態（サーバー接続／WSLディストリ／プロジェクト／モデル／サンドボックスモード／プロセス所有権状態）をステータス表示する | 必須 |
| F-08a | 通信異常またはapp-server子プロセスの異常終了を検知した場合、新しいapp-serverプロセスを起動し直せる | 必須 |
| F-08b | GUIまたはapp-server再起動後、保存済みthread一覧を取得し、対象threadを選択して会話を再開できる（thread本体はCodex側を正本とする。[8.1節](#81-データ保存方針gui側-vs-codex側)参照） | 必須 |
| F-08c | app-server再起動後、GUIが最後に認識したturn状態とCodex側の永続状態を**調停（reconciliation）**する。**PoCで実機確認済み**（[10節](#10-実装フェーズ)フェーズ1完了）: `thread/read`（`includeTurns: true`）で得られる各turnの`status`フィールドは`"completed"`/`"interrupted"`/`"failed"`/`"inProgress"`の4値であり、app-serverプロセスをSIGKILLで強制終了した直後に別プロセスから読み出しても、当該turnは正しく`"interrupted"`として永続化されていることを確認した（取りこぼしや誤った"completed"化は観測されなかった）。したがって調停ロジックは、thread全体の`status`（`notLoaded`/`idle`/`systemError`/`active`。これはapp-serverプロセスとの接続状態を表す別概念であり、turnの完了可否とは混同しない）ではなく、**対象turn自身の`status`フィールドを直接参照する**。`"completed"`→完了、`"interrupted"`→中断、`"failed"`→エラー（`error`フィールド参照）、`"inProgress"`→前回セッションが応答を受け取れないまま終了した可能性が高く「状態不明」として扱い、`turn/start`を自動再送しない（二重実行防止。[N-17](#42-非機能要件)、[N-22](#42-非機能要件)） | 必須 |
| F-09 | 複数スレッド（会話）を管理できる | 推奨 |
| F-09a | thread一覧は`thread/list`のcursorベースページングを用いて取得し、初回に全件をメモリへ読み込まない | 推奨 |
| F-10 | Git状態（変更ファイル数・ブランチ等）を表示する | 任意 |
| F-11 | MCPサーバーの接続状態を表示する | 任意 |
| F-12 | ログビューアを提供する | 任意 |
| F-13 | **主構成（stdio直結）では対象外**（子プロセスはGUIのライフタイムに紐づくため）。[5.4節](#54-代替構成優先順位付き)の代替構成（daemon+proxy、または自作ブリッジ）を採用する場合、GUI終了時の挙動は次のF-13a〜cの3操作として個別に提示する（「サーバーを残す/終了する」の二択では、daemonとproxyの所有権の違いを表現できないため） | 任意（代替構成採用時のみ） |

## 5. アーキテクチャ設計

### 5.1 通信方式（主構成: stdio直結）

- Windows GUI（Tauri Rustバックエンド）は`wsl.exe`を子プロセスとして起動し、その標準入力・標準出力を直接パイプ接続する。ネットワークポートは使用しない。
- 起動コマンド例: `wsl.exe -d <ディストリ名> --exec codex app-server --listen stdio://`
  - `--exec`（`-e`）はWSLの既定ログインシェルを介さず直接コマンドを実行するオプション。
  - 引数はシェルを介さず配列で渡し、`bash -lc`やシェルスクリプト経由を避けることで、引用符問題とシェルインジェクションのリスクを減らす。
- 通信フォーマットはJSONL（改行区切りJSON、JSON-RPCに準じた形式）。これはapp-serverの既定・最も実績のあるトランスポートである。
- 受信する構造化イベントの種類は変わらない: 会話メッセージ（ユーザー／アシスタント）、reasoning状態、コマンド実行要求・実行結果、ファイル変更（diff）、承認要求、エラー。

> **この構成を主構成とする理由**
> - WebSocketトランスポート（`--listen ws://`）は公式に「experimental and unsupported」と明記されている一方、stdioは既定・最も実績のある経路である。
> - リスニングポートが存在しないため、ポート管理・ポート競合・なりすまし接続・WSLネットワーク設定差異・Origin/HTTP Upgrade処理・WebSocket認証といった懸念事項が構造的に発生しない。
> - `wsl.exe`の子プロセスとしてGUIが直接所有するため、プロセス所有権（[N-14](#42-非機能要件)）が自明になる。

> **PoC検証済み（2026-07-18、[10節フェーズ1](#10-実装フェーズ)）**
> - `wsl.exe -d <distro> --exec <絶対パス> app-server`の引数配列渡しで、`initialize`〜turn完了までの一連の流れが実機で動作することを確認した。
> - stdio直結時、GUI（親プロセス）を`SIGKILL`で強制終了しても子プロセス（app-server）は孤児として残らないことを確認した（単発の手動テストであり、実GUI実装での再現性は別途確認する）。
> - GUI再起動のたびにapp-serverを起動し直す設計でも、[F-08b](#41-機能要件)「thread再開」はCodex側のthread永続化・resume機能（`thread/list`/`thread/resume`）により成立することを確認した。
>
> 検証に使用したスクリプト: [poc/phase1-poc.mjs](../poc/phase1-poc.mjs)

### 5.2 プロセス起動フロー（主構成）

**初回セットアップ（codex実行ファイルの絶対パス解決。[N-20](#42-非機能要件)/[N-21](#42-非機能要件)）**

```text
1. 対象WSLディストリビューションを選択する
2. codex実行ファイルを探索する（固定された探索コマンドのみ実行し、ユーザー入力をコマンド文字列へ埋め込まない）
3. 絶対パスを取得する
4. 実行可能性とバージョンを検証する
5. settings.jsonへ絶対パスを保存する
```

**通常起動**

```text
1. Rustバックエンドが wsl.exe を子プロセスとしてspawnし、stdin/stdoutをパイプで取得する
   wsl.exe -d <ディストリ名> --exec <保存済みcodex絶対パス> app-server --listen stdio://
   （保存済み絶対パスが無効な場合はapp-serverを起動せず、初回セットアップを再度案内する。N-21）
2. 起動直後からstdout/stderrを別タスクで継続的に読み出し開始（N-19）
3. initializeリクエストを送信する
4. initialize応答を検証し、app-serverであること・バージョンを確認する（N-15）
5. initialized通知を送信する（`initialize`→`initialized`はLSPと同様、他メソッドを呼ぶ前に必須のハンドシェイク）
6. 利用可能状態へ遷移し、保存済みthread一覧を取得する（[F-09a](#41-機能要件)のページングに従う）
7. プロジェクト／threadを開く（新規作成 または 既存threadのresume。[F-08b](#41-機能要件)）
```

推奨実装（Tauri Rust側）:

```rust
use std::process::{Command, Stdio};

// codex_path は N-20 に基づき settings.json から取得した絶対パス（例: "/home/user/.local/bin/codex"）
let child = Command::new("wsl.exe")
    .args([
        "-d", "Ubuntu",
        "--exec", &codex_path, "app-server", "--listen", "stdio://",
    ])
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::piped())
    .spawn()?;

// stdout / stderr は起動直後から別タスクで継続的にドレインすること（N-19）。
// 放置するとOSパイプバッファが満杯になり子プロセスがブロックする。
```

- ディストリ名は設定ファイル（`settings.json`）で指定可能にする（既定値のハードコーディングを避ける）。
- `-d`と`--exec`の順序・構文はWSLのバージョンによって挙動が変わりうるため、PoCで実機確認する。
- `--exec`はWSLの既定ログインシェルを介さないため、`~/.local/bin`、`~/.npm-global/bin`、nvm/Volta/mise/asdf管理下のbin等にインストールされた`codex`は、`.bashrc`/`.profile`のPATH設定を経由しても解決できない。そのため相対コマンド名`codex`ではなく絶対パスを使用する（上記初回セットアップ参照）。

### 5.3 終了フロー（主構成）

- GUI終了時、子プロセス（wsl.exe / app-server）へ標準入力のクローズ（EOF）またはプロセス終了シグナルを送り、確実に終了させる。
- GUIが異常終了（クラッシュ）した場合に子プロセスが孤児として残らないか、PoCで確認する（[10節](#10-実装フェーズ)）。必要であればWindows Job Object等で子プロセスのライフタイムを親プロセスに紐づけることを検討する。
- 主構成では「GUIを閉じてもサーバーを残す」設計は採用しない（[F-13](#41-機能要件)は主構成では対象外）。サーバー永続化が必要な場合は[5.4節](#54-代替構成優先順位付き)の代替構成を検討する。
- いずれの構成でも `wsl --shutdown` は使用しない（他プロセスへの影響を避けるため）。

### 5.4 代替構成（優先順位付き）

主構成（stdio直結）で致命的な問題（例: thread resumeが機能しない、孤児プロセス問題が解決できない、複数クライアントからの同時接続が必要になった等）が判明した場合に限り、以下を検討する。

> **位置づけの明確化**: 以下のA〜Cはいずれも「主構成を置き換える新本命」ではない。主構成（stdio直結）は変更せず、それでサーバー常駐（[F-13](#41-機能要件)相当）が本当に必要になった場合にのみ、この節を評価する。

**A. `app-server daemon` + `codex app-server proxy`（要追加PoC。優先フォールバックではなく実験的候補）**

> **成熟度に関する重要な訂正**: 実機の`codex app-server --help`（`codex-cli 0.144.5`で確認）でサブコマンドの存在自体は確認できたが、公式CLIリファレンスでは関連機能（`codex remote-control`、`daemon`管理）は成熟度「Experimental」に分類されており、次のように明記されている: 「Managed remote-control clients and SSH remote workflows use these commands; they aren't a replacement for `codex app-server --listen` when you're building a local protocol client.」（管理された remote-control クライアントやSSHリモートワークフローがこれらのコマンドを使うのであって、ローカルプロトコルクライアントを構築する際の`codex app-server --listen`の代替ではない）。したがって本構成は「公式サポート範囲内で完結する優先フォールバック」ではなく、**採用前に独立したPoCで動作・ライフサイクル・所有権を確定させるべき実験的候補**として扱う。

判明している機能（実機`--help`確認、成熟度はCLIリファレンスに基づく）:
- `codex app-server daemon start` / `restart` / `stop`: ローカルapp-serverデーモンを起動・再起動・停止するサブコマンド
- `codex app-server daemon version`: ローカルCLIバージョンと稼働中app-serverデーモンのバージョンをJSONで出力する
- `codex app-server proxy`: 稼働中のapp-serverデーモンのcontrol socket（既定は`$CODEX_HOME/app-server-control/app-server-control.sock`）へstdioバイトを中継するサブコマンド（`--help`表記: "Proxy stdio bytes to the running app-server control socket"）

```text
Windows GUI
    │ stdin/stdout（wsl.exe子プロセス経由）
    ▼
① wsl.exe -d <distro> --exec <codex絶対パス> app-server daemon start
   （※「未起動時のみ起動する」という設計意図は--helpの説明文からの推測であり、
      実際の冪等性・競合時の挙動は未確認。下記の既知Issue参照）
② wsl.exe -d <distro> --exec <codex絶対パス> app-server proxy
    │ Unixドメインソケット（app-server-control.sock）
    │ ※ただし上を流れるのはJSONLではなく、WebSocketの
    │   HTTP Upgradeハンドシェイク＋WebSocketフレームをそのまま運ぶバイト列
    ▼
codex app-serverデーモン（WSL内で常駐する想定。ただしdaemon/proxyの所有権はGUIとは別に管理する）
```

> **プロトコルに関する訂正**: `codex app-server proxy`は、指定したUnixソケットとstdin/stdoutの間で**バイトをそのまま中継するだけ**であり、公式READMEには「The proxied stream carries the websocket HTTP Upgrade handshake followed by websocket frames.」と明記されている。つまりWindows GUI側から見えるstdin/stdout上のデータは、主構成（5.1節）のJSONLではなく、**WebSocketのHTTP Upgradeハンドシェイクとフレーム**である。プロセスの起動・stdin/stdoutの読み書き自体（子プロセス管理コード）は主構成と共用できるが、その上に実装するプロトコルcodec（メッセージの送受信ロジック）は別物になる。したがって、トランスポート層を最初から抽象化しておくことを推奨する:
>
> ```rust
> trait AppServerTransport {
>     async fn send(&mut self, message: ClientMessage) -> Result<()>;
>     async fn receive(&mut self) -> Result<ServerMessage>;
>     async fn close(&mut self) -> Result<()>;
> }
>
> struct JsonlStdioTransport;      // 主構成（5.1〜5.3）
> struct WebSocketStreamTransport; // 代替構成A（proxy経由）・代替構成C（--listen ws://）で共用可能
> ```
>
> 主構成のstdioパイプ用コードをそのまま`proxy`へ接続しても、JSONLクライアントとしては動作しない点に注意する。

**所有権の分離（[N-14a〜d](#42-非機能要件)）**: 本構成にはGUIが起動するプロセスが2種類あり、所有権を一括りにできない。
- `proxy`: GUIが直接spawnする子プロセスなので常にowned（[N-14b](#42-非機能要件)）
- `daemon`: 既に存在していた可能性（他のCodexクライアントが起動した、`proxy`自身が暗黙に再起動した等）があるため、`daemon start`をGUIが呼んだという事実だけではownedと判定しない（[N-14c](#42-非機能要件)/[N-14d](#42-非機能要件)）

**起動確認の手順（`daemon version`は`initialize`検証の代替にならない）**: `daemon version`はCLIとdaemonのバージョン情報を事前に得られるだけであり、実際に接続した相手がapp-serverであること・ハンドシェイクが成立すること・必須APIが利用可能であることまでは示さない。[N-15](#42-非機能要件)を満たすには、以下を全段階実行する必要がある。

```text
1. daemon versionでCLIとdaemonのバージョンを事前確認する
2. proxyへ接続する
3. WebSocket Upgradeを完了する
4. initializeを送信する
5. initialize応答をスキーマ検証する
6. initialized通知を送信する
7. 必須APIの利用可能性を確認する
```

**既知の不具合報告（要PoC再確認）**: `codex-cli 0.131.0`/`0.133.0`時点のGitHub Issueとして、以下が報告されている（`0.144.5`で再現するかは未確認）。
- Issue #23572（closed as not planned）: `codex app-server proxy`が、正常な初期化リクエストを送っても標準出力・標準エラーが空のまま終了コード0で終了するケースが報告されている
- Issue #24542（open）: `codex app-server proxy`が非管理（unmanaged）のapp-serverを暗黙に再生成し、managed daemonへの移行を妨げる競合状態が報告されている（「app server is running but is not managed by codex app-server daemon」というエラーが発生し、原因の診断情報が得られない）

これらを踏まえ、代替構成Aの追加PoC項目には少なくとも以下を含める（[10節](#10-実装フェーズ)参照）:

```text
□ daemon startの冪等性・多重起動時の挙動（古いsocketが残っている場合、
  起動途中の場合、unmanaged app-serverがsocketを所有している場合を含む）
□ proxy起動前後のdaemon PIDを比較する
□ proxyが別のunmanaged app-serverを暗黙起動しないか確認する
□ proxyが接続失敗時に非ゼロ終了コードを返すか確認する
□ proxyが終了コード0・出力なしで終了するケースを検出できるか（Issue #23572）
□ control socketの所有PID・パーミッションを確認できるか（N-11a）
□ daemon stop後、proxyがdaemonを再生成しないか確認する（Issue #24542）
□ daemon stop実行時、接続中のproxyセッションがどう扱われるか
```

GUI側は、proxyの起動成功を「プロセスが生きていること」だけで判定せず、上記の7段階（WebSocket Upgrade成功・`initialize`応答受信・`initialized`送信完了）まで確認できて初めて「接続済み」とする。

- 利点: app-server本体をWSL内でデーモンとして常駐させつつ、Windows側のプロセス起動・パイプ管理コードは主構成（5.1〜5.3）と共用できる可能性がある。
- 自作コードが（トランスポートcodecの追加実装を除けば）最小限で済む。
- **このPoCがすべて通った場合に限り、正式な代替構成へ昇格させる。** 通らない場合はB（自作ブリッジ）を検討する。

**B. 自作ブリッジ（Aの追加PoCで要件を満たせないと判明した場合のみ）**

```text
Windows GUI
    │ TCP / WebSocket（自作プロトコル）
    ▼
WSL2内の自作中継プロセス（Node.js等・軽量）
    │ stdio（JSONL）
    ▼
codex app-server（stdio既定モード・常駐）
```

- 中継プロセスはWindows GUI側の接続が切れても終了させずWSL内で生かし続け、app-serverとのstdio接続を維持できる。
- デメリットは自作の中継プロセスがもう一つの保守対象になる点（プロセス監視・異常終了時の再起動ロジックを自前で持つ必要がある）。`daemon` + `proxy`（A）の追加PoCで要件を満たせないと確認された場合のみ採用する。

**C. `--listen ws://`（開発・検証用途に限定）**

- 公式に「experimental and unsupported」と明記されているため、常用構成としては採用しない。PoCでのデバッグや、ブラウザ製デバッグツールからの一時的な接続確認等の用途に限定する。
- 採用する場合は[N-11](#42-非機能要件)〜[N-13](#42-非機能要件)（TCP WebSocketでのcapability tokenによる認証必須化）を満たすこと。

**採用判断はいずれもフェーズ1のPoC結果を踏まえて行う**（[10節](#10-実装フェーズ)参照）。

### 7.3 承認UI

**PoCで実機確認済み**（2026-07-18、[poc/phase1c-approval-network.mjs](../poc/phase1c-approval-network.mjs)）。承認要求（例: `item/commandExecution/requestApproval`）は次のような形で届く（実機での実例、抜粋）:

```json
{
  "method": "item/commandExecution/requestApproval",
  "id": 0,
  "params": {
    "threadId": "...", "turnId": "...", "itemId": "call_...",
    "command": "/bin/bash -lc \"curl -s -o /dev/null -w '%{http_code}\\n' https://example.com\"",
    "cwd": "/home/user",
    "commandActions": [{ "type": "unknown", "command": "curl ..." }],
    "availableDecisions": ["accept", { "acceptWithExecpolicyAmendment": { "execpolicy_amendment": ["curl", "-s", "..."] } }, "cancel"]
  }
}
```

固定の「許可する／今回だけ拒否／中止」3ボタンではなく、**リクエストごとの`availableDecisions`配列からボタンを動的に構築する**（PoCで実際に確認: あるリクエストでは`accept`/`acceptWithExecpolicyAmendment`/`cancel`のみが提示され、`decline`や`acceptForSession`は含まれていなかった）。決定値は`CommandExecutionApprovalDecision`型: `"accept"`（今回だけ許可）／`"acceptForSession"`（セッション中許可）／`{"acceptWithExecpolicyAmendment":{...}}`（提案された実行ポリシー変更ごと許可）／`{"applyNetworkPolicyAmendment":{...}}`（ネットワークポリシー変更ごと許可）／`"decline"`（対象操作のみ拒否してturnを継続する）／`"cancel"`（turn全体を停止する）。「decline」と「cancel」は意味が異なるため、UI上でも明確に区別する。

表示イメージ（`availableDecisions`に応じてボタン内容は変わる）:

```text
Codex wants to run:

curl -s -o /dev/null -w '%{http_code}\n' https://example.com

[許可する] [ポリシーを緩めて許可] [中止]
```

- ターミナルラッパー方式との最大の差別化ポイント。承認要求を構造化イベントとして受け取り、専用UIで提示する。
- 各承認要求は、app-serverが発行する一意なrequest ID（`ServerRequest`の`id`）を内部状態として保持する。応答は`{"id": <同じid>, "result": {"decision": ...}}`の形でapp-serverへ返す。
- 応答済みのrequest IDへ二重に応答を返さない。
- 通信が切断されている間、承認ボタンは無効化する。
- 承認待ちのままapp-serverが終了した場合は「失効」と表示する。
- PoCで確認: 承認応答送信後、`serverRequest/resolved`通知が届く。これを「サーバー側で処理済み」のUIフィードバックに使える。
- **未解明の挙動（要P1追加調査）**: PoCで、`availableDecisions`に`"accept"`が含まれていたにもかかわらず`"accept"`を送ったところ、app-serverのstderrに`approval policy is UnlessTrusted; reject command — you cannot ask for escalated permissions if the approval policy is UnlessTrusted`というエラーが記録された（turn自体はエラー落ちせず進行した）。`availableDecisions`に列挙されていることと、そのポリシー下で実際に有効なことは必ずしも一致しない可能性がある。ネットワークアクセス等エスカレーションが必要なケースでは`acceptWithExecpolicyAmendment`のような、提案された変更ごと受理する決定を使う必要があるのかもしれない。GUI実装前にP1として原因を切り分ける。

### 8.1 データ保存方針（GUI側 vs Codex側）

会話履歴の二重管理を避けるため、正本の所在を明確にする。

| 種別 | 正本 | GUI側での扱い |
|---|---|---|
| 会話本文・turn・item・コマンド実行履歴・reasoningイベント | Codex側（app-server / thread） | **恒久保存はしない**（[N-09a](#42-非機能要件)）。threadを開く際に`thread/read`で初期状態を取得し、以後は受信イベントでプロセスメモリ上の状態を更新する。GUI終了後まで残る恒久キャッシュ（SQLite等）は作らない |
| 進行中turnの最小限の操作ジャーナル（thread ID・turn ID・request ID・送信時刻・最後に受信したイベント種別/時刻・ローカル認識状態） | GUI側 | クラッシュ復旧・二重実行防止のためSQLite等に保存してよい（[N-22](#42-非機能要件)）。本文・コマンド出力・reasoning本文は含めない |
| 最近使ったプロジェクト、thread ID・表示名・最終アクセス時刻 | GUI側 | 表示補助データとしてSQLite等に保存する |
| UI設定・ウィンドウ状態・お気に入り | GUI側 | 保存する |
| 接続したapp-serverのバージョン情報 | GUI側 | 保存する（互換性チェック用、[N-10](#42-非機能要件)） |

GUI側で会話本文を恒久的に複製・キャッシュすると、Codex側履歴との不整合、イベント取りこぼし、同一threadの二重登録、Codex CLI更新後のデータ形式差、コード内容の保存範囲拡大といった問題が生じる。表示中のプロセスメモリ上での保持（画面再描画のたびに`thread/read`を呼び直さないための最適化）と、SQLite等への恒久保存は区別すること。オフライン表示を要件にする段階になって初めて、恒久キャッシュの追加を検討する。

## 9. セキュリティ仕様

| 項目 | 方針 |
|---|---|
| 通信経路（主構成） | Windows GUIは`wsl.exe`の子プロセスを標準入出力パイプで直結する。ネットワークポートを一切開かないため、ポートスキャン・なりすまし接続・外部プロセスからの不正接続といった、リスニングソケット特有の攻撃面が構造的に存在しない |
| 認証情報の扱い | OpenAI APIキー・ChatGPT/Codex認証トークンはWindows GUI側に一切保持・表示しない。認証はWSL内のCodexに一任する |
| 破壊的操作の回避 | `wsl --shutdown`等、対象アプリ以外のWSLプロセスに影響する操作は行わない。終了対象は自らが起動した（owned）プロセスに限定する（[N-14](#42-非機能要件)） |
| 代替構成C（TCP WebSocket）採用時のバインドアドレス | `ws://127.0.0.1:PORT`に固定。`0.0.0.0`等の外部公開は行わない |
| 代替構成C（TCP WebSocket）採用時の認証 | `--ws-auth capability-token`を必須とし、トークンは`--ws-token-file`で渡す（コマンドライン引数に直接渡さない）。トークンファイルの権限はWSL側で0600とする（[N-11](#42-非機能要件)〜[N-13](#42-非機能要件)） |
| 代替構成A（daemon + proxy、Unixソケット経由）採用時の信頼境界 | TCP WebSocketとは異なる信頼境界として扱う。ソケットファイル（`$CODEX_HOME/app-server-control/app-server-control.sock`）の所有者・パーミッションを実機で確認し（`stat`コマンド）、他ユーザーから接続可能な権限であれば採用しない（[N-11a](#42-非機能要件)/[N-11b](#42-非機能要件)） |
| 代替構成採用時のOriginヘッダの扱い（要検証） | 公式ドキュメントは`/healthz`エンドポイントについて「Originヘッダを持つリクエストは403で拒否する」と明記しているが、これがWebSocketアップグレード処理そのものにも適用されるかは一次情報からは確認できていない。代替構成を採用する場合はPoCで実際の挙動を確認したうえで、ブラウザ等からの意図しない接続（drive-by接続）を防げるか判断する |
| ローカル保存データの扱い | 診断ログにはプロジェクト名・パス等が含まれ得るため、クラウド同期対象外のディレクトリに保存する（[N-09](#42-非機能要件)）。GUI側は会話本文・reasoning本文・コマンド出力を恒久保存しない方針とする（[N-09a](#42-非機能要件)、[8.1節](#81-データ保存方針gui側-vs-codex側)）。第三者と共有するログ・スクリーンショットには機密コードが写り込んでいないか確認する |

## 11. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| `codex`実行ファイルのPATH解決失敗 | `--exec`はログインシェルを介さないため、`.bashrc`等でPATHを設定している環境（nvm/Volta/mise/asdf管理下等）では`codex`コマンドが見つからない | 絶対パスを初回セットアップで解決し設定に保存する（[N-20](#42-非機能要件)/[N-21](#42-非機能要件)） |
| 代替構成Aの通信プロトコルの誤解 | `codex app-server proxy`はstdin/stdout上でWebSocket（HTTP Upgrade＋フレーム）を中継するのであり、JSONLではない。主構成のstdioパイプ処理コードをそのまま流用するとプロトコル不一致で動作しない | トランスポート層をトレイト等で抽象化し、JSONL用とWebSocketストリーム用のcodecを別実装として用意する（[5.4節](#54-代替構成優先順位付き)A） |
| 子プロセスの孤児化 | GUIクラッシュ時にwsl.exe/app-server子プロセスが残り続ける可能性 | **PoCで検証済み（2026-07-18、[10節](#10-実装フェーズ)P0）**: SIGKILLでの強制終了後も孤児プロセスは残らないことを確認。ただし今回は単発の手動テストであり、実際のGUI実装（Tauri Rustバックエンド）での再現・多数回試行での安定性は別途確認する。必要であればWindows Job Object等でライフタイムを親プロセスに紐づける |
| stdout/stderr未分離によるデッドロック | 子プロセスの出力を読み出さないとOSパイプバッファが満杯になりプロセスが停止する | 起動直後から専用タスクで両方を継続的にドレインする（[N-19](#42-非機能要件)） |
| thread再開（resume）が機能しない可能性 | GUI/app-server再起動のたびに新規プロセスを起動する設計のため、Codex側のthread永続化・resume機能に依存する | **PoCで検証済み（2026-07-18、解消）**: 別プロセスからの`thread/list`・`thread/resume`・resume後のturn続行を確認。[F-08b](#41-機能要件)は主構成のまま成立する。5.4節Aへの切り替えは不要と判断 |
| 実行中turnの二重実行 | 切断・再接続時に同一リクエストを自動再送すると、コマンドやファイル変更が二重実行される恐れがある | リクエストの自動再送を禁止し、thread/turn状態を問い合わせてから判断する（[F-08c](#41-機能要件)、[N-17](#42-非機能要件)） |
| プロセス所有権の誤認 | 既存プロセスに接続した場合、それを自分のものと誤認し、終了操作で他用途のプロセスを巻き込む恐れ | owned/attached/externalの状態を明示的に管理し、終了操作はownedのみに限定する（[N-14](#42-非機能要件)）。主構成（stdio直結）ではGUIが子プロセスを直接spawnするため常にownedとなり、この問題は発生しない |
| **（代替構成A採用時のみ）** daemonとproxyの所有権混同 | `proxy`はGUIがspawnした子プロセスだが、`daemon`は既に存在していた可能性・他クライアントが起動した可能性・`proxy`自身が暗黙に再生成した可能性があり、単純に「GUIが`daemon start`を呼んだのでowned」とは判定できない | proxyとdaemonの所有権を別管理し、daemonはPID比較等で新規起動を確認できない限りownedと判定しない（[N-14a〜d](#42-非機能要件)） |
| UIパフォーマンス劣化 | トークンdeltaごとに逐次UI更新すると、長い応答や大量コマンド出力でUIが重くなる | 16〜50ms単位でのバッチ更新を行う（[N-18](#42-非機能要件)） |
| app-server過負荷時のエラー未処理 | リクエスト飽和時に返る`-32001`エラーを単純失敗として扱うと、再試行可能な状況で処理が止まる | 指数バックオフ＋ジッターでの再試行を実装する（[N-16](#42-非機能要件)） |
| app-server APIのバージョン差・実験API変更 | Codexアップデートに伴うAPIのバージョン差、および一部の実験API（`capabilities.experimentalApi`でオプトインする範囲）が変更される可能性がある。stdio自体はexperimentalではなく既定・安定したトランスポートであり、この点を混同しない | 対応バージョンを固定し、そのバージョンから生成したスキーマ（`generate-ts`/`generate-json-schema`）をビルドに組み込みランタイム検証する（[N-10](#42-非機能要件)）。MVPでは`experimentalApi`を有効化しない（[N-23](#42-非機能要件)） |
| WSLディストリ名のハードコーディング | 環境によって既定ディストリ名が異なる | 設定ファイルでディストリ名を指定可能にする |
| 対応Codex CLIバージョンの未確定 | 現時点で本仕様が前提とする最小バージョンが未確定 | PoCで動作確認したバージョンを本仕様書に明記する（[N-07](#42-非機能要件)） |
| 診断ログの肥大化・情報漏洩 | 診断ログにプロジェクト名・パス等が含まれ、無制限に肥大化・クラウド同期される懸念 | 保持上限の設定（[N-08](#42-非機能要件)）、同期対象外ディレクトリへの保存（[N-09](#42-非機能要件)）、GUI側での会話本文の恒久的な複製保存を行わない（[N-09a](#42-非機能要件)、[8.1節](#81-データ保存方針gui側-vs-codex側)） |
| **（代替構成A採用時のみ）** `app-server daemon`/`remote-control`がCLIリファレンス上Experimental | 「ローカルプロトコルクライアントを構築する際の`codex app-server --listen`の代替ではない」と公式に明記されている | 5.4節Aを「優先フォールバック」ではなく「要追加PoCの実験的候補」として扱い、独立したPoCで動作・所有権を確定させてから正式採用を判断する |
| **（代替構成A採用時のみ）** `proxy`の既知不具合（GitHub Issue） | Issue #23572（`0.131.0`、closed as not planned）: `proxy`が終了コード0・出力なしで終了するケースが報告されている。Issue #24542（`0.133.0`、open）: `proxy`が非管理app-serverを暗黙に再生成し、managed daemonへの移行を妨げる競合状態が報告されている。`codex-cli 0.144.5`での再現有無は未確認 | 採用前に5.4節AのPoCチェックリストで再現有無を確認する。GUI側は「プロセスが生きている」だけで接続成功と判定せず、WebSocket Upgrade成功・`initialize`応答受信・`initialized`送信完了まで確認する |
| **（代替構成C採用時のみ）** WebSocketトランスポート（`--listen ws://`）が「experimental and unsupported」 | 公式README・ドキュメントに明記されている | 主構成（stdio直結）を採用する限り本リスクの影響を受けない。[5.4節](#54-代替構成優先順位付き)Cの用途を開発・検証用に限定する |
| **（代替構成C採用時のみ）** ローカル無認証TCP WebSocketへの意図しない接続 | ブラウザ等からの接続を完全には排除できない可能性がある（Originヘッダ検証の適用範囲は未確認、[9節](#9-セキュリティ仕様)） | capability token認証を必須化する（[N-11](#42-非機能要件)〜[N-13](#42-非機能要件)） |
| **（代替構成C採用時のみ）** app-server実装の未成熟さ（既知Issue） | GitHub Issue #19688（UDS-over-WebSocketハンドシェイク関連）など、既知の不具合報告が存在する | 実装開始前にopenai/codexのIssueトラッカーを確認する |
| WSL2ネットワーク設定の環境差異（代替構成採用時のみ） | `localhostForwarding`が無効化されている環境ではWebSocket/Unixソケット代替構成が使えない | 主構成（stdio直結）はこの問題の影響を受けない。代替構成採用時のみ起動時ヘルスチェックとドキュメント化で対応 |

## 13. 結論（採用構成まとめ）

```text
Windows:
Tauri 2 + React + TypeScript + Monaco Editor

プロセス境界（主構成 A0）:
Tauri Rustバックエンド
    │ stdin/stdout（パイプ、ネットワークポートなし）
    ▼
wsl.exe --exec <codex絶対パス> app-server --listen stdio://

認証:
OpenAI/ChatGPT認証情報はWSL内のCodexだけが保持する

会話履歴:
Codex側のthreadを正本とする。GUI側はthread参照情報＋最小操作ジャーナルのみ保存する

GUIローカル保存:
設定・プロジェクト一覧・thread参照情報・操作ジャーナル・UI状態のみ

プロジェクト:
WSL Linuxファイルシステム（~/src/配下）

優先順位（今回発見したdaemonは主構成を置き換える新本命ではない）:
A0. 主構成: app-server stdio直結
A1. 障害時の復旧: 新しいstdio app-serverを起動し、thread/resumeで復帰
B0〜B2. 常駐が本当に必要になった場合: daemon + proxyを独立PoCで検証
        （所有権・socket権限・暗黙起動・停止挙動が確認できた場合のみ正式な代替構成へ昇格）
C. 最終手段: 自作ブリッジ（B0〜B2で要件を満たせない場合のみ）
D. 開発確認専用: --listen ws://（常用構成としては採用しない）
```

この構成により、Windows版Codexアプリの不安定なUI・実行環境切り替えに依存せず、安定したWSL版Codex CLIの実行系と使いやすいWindowsネイティブGUIを組み合わせた専用クライアントを実現する。

主構成をWebSocketからstdio直結へ切り替えたことで、WebSocketの実験的トランスポート、ポート競合、ローカル認証、WSLネットワーク設定差異、サーバー残存モデルといったリスクの大部分を設計段階で回避できる。stdioはapp-serverの既定トランスポートであり、公式README上で「experimental and unsupported」とされているのはWebSocketトランスポートのみである（stdio自体を不支持とする記述は一次情報にはない）。一方、公式CLIリファレンスでは`codex app-server`コマンド自体・および`codex remote-control`/`app-server daemon`によるサーバー常駐機能はいずれも成熟度「Experimental」に分類されており、「ローカルプロトコルクライアントを構築する際の`codex app-server --listen`の代替ではない」と明記されている。したがって今回発見した`daemon`機能は、**主構成を置き換える新本命ではなく、stdio直結でサーバー常駐が必要になった場合にのみ検証する、バージョン依存の実験的候補**と位置づける（[5.4節](#54-代替構成優先順位付き)A）。残る中心的な課題は、Codexアップデートに伴うapp-server APIのバージョン差・一部の実験API（`capabilities.experimentalApi`でオプトインする範囲。MVPでは無効化する、[N-23](#42-非機能要件)）の変更可能性、`codex`実行ファイルのPATH解決、thread resumeの実動作であり、対応Codexバージョンの固定・生成スキーマによるランタイム検証・フェーズ1PoCでの確認によって管理可能な範囲に収める。
