## A. 公開準備の状態

### A-1. 公開用リポジトリの情報漏洩監査 ★最重要

これまで実機検証の記録として、Windowsユーザー名・ホスト名・`C:\Users\...`・`/home/user/...`・WSLのgateway IP・実アカウントのクレジット残高・実機固有パス・誤コミットした`app.exe`などが記録されてきた。**現在のファイルを直すだけでは過去コミットからは消えない**ため、Git履歴全体の監査が要る。

判断は次の3分類で行う。

```text
公開可能
公開したくないが秘密ではない
絶対に公開してはいけない
```

APIキーらしき文字列は簡易検索では見つかっていないが、それは履歴監査の代わりにはならない。

#### 予備調査の結果（2026-08-10 実施）

現時点で機械的に確認できた事実を記録する。**これは予備調査であり、本監査の代替ではない。**

| 対象 | 現在のファイル | 履歴 |
| --- | --- | --- |
| `user`（Windowsユーザー名） | 3ファイル | 7コミット |
| `user`（WSLユーザー名） | 16ファイル | 19コミット |
| `C:\Users` | — | 10コミット |
| クレジット残高 `1234.5678900000` | 3ファイル | 1コミット |
| WSL gateway `172.21.112.1` | 3ファイル | — |
| 誤コミットした`app.exe` | 追跡停止済み | **8個のblobが履歴に残存（各約10MB、計約80MB）** |

個別に判断が要るもの:

- **`app/src-tauri/tauri.conf.json` の旧 `identifier: "com.user.wslcodexgui"`** — 当時はバンドル識別子にユーザー名が入っていた。**公開後に変更するとアップグレード経路が壊れる**ため、初回公開前に変更した（結果は[A-1の完了記録](#a-1-公開用リポジトリの情報漏洩監査-最重要)を参照）。
- **クレジット残高** — [creditBadge.test.mjs](../app/src/creditBadge.test.mjs)・[creditBadge.ts](../app/src/creditBadge.ts)・[残項目.md](残項目.md)に実アカウントの残高が実データとして入っている。テストの値としては架空の数値で十分機能するため、差し替えるのが妥当。
- **WSL gateway IP** — [lib.rs](../app/src-tauri/src/lib.rs)のテスト値と仕様書の記録。`172.21.112.1`はWSLが割り当てるプライベートアドレスで秘密性は低いが、環境の特定に繋がるため「公開したくないが秘密ではない」に該当する。
- **`app.exe`のblob** — 履歴から消すにはリポジトリの書き換え（`git filter-repo`等）が必要。単独開発でforkも無いため実行は容易だが、コミットSHAがすべて変わる。**publicにする前に行うこと**（public化後の書き換えは、既にcloneされた履歴を回収できない）。

#### 進め方

1. 分類基準を決める（上記3分類）
2. 現在のファイルを是正する
3. 履歴の書き換えが必要なものを確定する（`app.exe` blobは確定、それ以外は分類次第）
4. 書き換えを実行し、ローカルで結果を検証する
5. **その後に**public化する

**→ 1〜4は完了（2026-10-24）**: ユーザーの判断で、Windows/WSLのユーザー名（小文字の単語として）を`user`に、実アカウントの残高を架空の値に置き換え、`target/release/app.exe`を全履歴から削除した（`git filter-repo`）。バンドル識別子は書き換えの直前に`io.github.fuyukiyoneyama.wslcodexgui`へ変更済み。作者名・作者アドレス（元から全コミットがGitHubのnoreplyアドレス）とGitHubユーザー名、WSLのgateway IPはそのまま。書き換え後の履歴は新しい非公開リポジトリ`FuyukiYoneyama/WslCodexGui`へ入れ直し、元のリポジトリは`FuyukiYoneyama/WslCodexGui-old`（非公開）として残した。public化（5）は他の項目が終わってから。

**→ 5も完了（2026-10-25）**: 監査済みの[FuyukiYoneyama/WslCodexGui](https://github.com/FuyukiYoneyama/WslCodexGui)をpublic化した。v0.5.61のReleaseとインストーラーはログインなしのURLから取得でき、ダウンロードしたインストーラーのSHA-256はリリースノートと一致した。

#### 実施方法（Windowsサンドボックス）

開発PCにはRust・Node・WebView2・Codex・過去の設定などが揃っているため、「開発PCでは偶然動く」状態を見つけるには、何も入っていない使い捨て環境で試す。Windows 11 Proに付属するWindowsサンドボックスを使う（閉じると中身がすべて消え、毎回まっさらな状態から始まる）。

**準備（初回のみ。管理者権限と再起動が必要なので、ユーザーが行う）**

- 「Windows の機能の有効化または無効化」で「Windows サンドボックス」をオンにして再起動する。
- または管理者のPowerShellで次を実行して再起動する。

  ```powershell
  Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All
  ```

**サンドボックスの設定ファイル（例: `clean-install.wsb`）**

試験する版のインストーラを置いたフォルダだけを、読み取り専用で中に渡す。

```xml
<Configuration>
  <MappedFolders>
    <MappedFolder>
      <HostFolder>D:\Documents\WslCodexGui\app\src-tauri\target\release\bundle\nsis</HostFolder>
      <SandboxFolder>C:\Installer</SandboxFolder>
      <ReadOnly>true</ReadOnly>
    </MappedFolder>
  </MappedFolders>
  <Networking>Enable</Networking>
</Configuration>
```

**確認する手順（サンドボックスの中で）**

1. エクスプローラーで`C:\Installer`を開き、`WslCodexGui_<版>_x64-setup.exe`を実行する。SmartScreenの警告の出方を記録し、インストールする。
2. スタートメニューまたはデスクトップのショートカットから起動し、アイコンと表示を確認する（WebView2が足りているか）。
3. Codex CLIが無い状態で、接続パネルが「codexが見つからない」旨を案内し、接続ボタンが無効になることを確認する。
4. Windows-nativeモードの接続: 今回成功した手順では、既存のCodex CLIの`codex.exe`と`codex-code-mode-host.exe`をサンドボックス内のデスクトップへコピーして使った。サンドボックス内でCLIを起動してサインインする（サインイン画面はユーザーが操作する）。アプリで接続方式を「Windows側のcodex CLI」にし、コピーした`codex.exe`を指定して接続する。プロジェクトを選んで1往復会話できることを確認する。
5. 「設定」→「アプリ」からアンインストールし、インストール先・スタートメニュー・デスクトップのショートカット・アプリ一覧の登録が消えることを確認する。

**この方法で確認できないこと**

- **WSLモード**: サンドボックス内ではWSL2が動かない。WSLモードの確認は、Hyper-Vの仮想マシン（入れ子の仮想化を有効にしたWindows 11）にWSL2とCodex CLIを入れる方法になる（手間が大きい）。開発PCではWSLモードの動作を確認済み。
- **旧版からの更新**: サンドボックスは毎回まっさらなので、更新を試す場合は同じセッション内で旧版を入れてから新版を実行する。

**注意**

- インストーラはエクスプローラーから実行する。Claude desktopやCodexアプリ（いずれもMSIXパッケージ）のコマンド経由で実行すると、`%LOCALAPPDATA%`への書き込みがそのアプリ専用の領域に振り替えられ、実際の環境と違う結果になる（A-3、[残項目.mdの完了ログ](残項目.md#完了ログ)参照）。
- 結果は、試した版数・確認できた項目・確認できなかった項目を分けて、本節と残項目.mdの完了ログに記録する。

### A-5. GUI障害試験の判定

[残項目.md](残項目.md)に残っている実機試験。コードレビューでは代替できない。

- 承認要求中に切断
- 承認応答のwrite失敗 → 同一request IDで再試行
- 画像保存直後の送信防止
- 画像保存中のthread切替／切断

承認と画像は`React state / Tauri IPC / Codex app-server / 一時ファイル / 非同期event`をまたぐため、公開前に実機で終わらせる価値がある。

**→ 判定済み（2026-10-24、0.5.56）**: 画像の2件は合格。承認中の切断は、ダイアログが切断ボタンを覆う設計であり、ユーザー判断で現状維持。代替としてプロセス終了による切断を試し、ダイアログ消去と再接続を確認した。書込み失敗だけを起こす状況はGUIで再現できず、失敗時にダイアログを残すコードを確認した。両件の制約は記録済みで、追加の公開ゲートにはしない。試験中に見つかった「予期しない切断後に送信が`thread not found`で失敗し入力が消える」不具合と「切断の通知がない」問題は0.5.56で修正済み。詳細は[残項目.md](残項目.md)の完了ログ。

## C. 必須ではないもの

### C-1. コード署名

公開自体に必須ではない。未署名でもGitHub Releaseから配布できる。ただしWindows SmartScreenが「発行元不明」等の警告を出す可能性がある。

最初は**未署名である旨をREADMEとReleaseに明記して公開し**、利用者が増えてから署名を検討すればよい。個人開発で最初から証明書費用を負担する必要はない。

### C-2. SECURITY.md

あると良いが必須ではない。作るなら「脆弱性は公開Issueではなく○○へ報告」「対応対象バージョン」程度で十分。**メールアドレスを公開したくないなら無理に置かなくてよい。**

### C-3. CONTRIBUTING.md

一人開発で外部PRを積極的に募集しないなら不要。READMEに「Issues歓迎」「PRは事前にIssueで相談」程度でよい。

### C-4. 初回公開の条件に含めないもの

- **`App.tsx`の分割** — 公開を止める理由にならない。着手時期は別途判断する。
- **`-32001`自動retry** — 不要。現在の（再送しない）方が安全。

## CI運用方針との関係

[CI運用方針](残項目.md)により、通常開発でGitHub Actionsは使わない。workflowは`workflow_dispatch`（手動）と`push: tags: ["v*"]`（リリースタグ）でのみ起動する。

上記手順4の`v<バージョン>`タグpushでCIを起動する。目的は「クリーンなGitHub環境でもリリース対象がビルド・テストできること」の確認。`workflow_dispatch`も実行すると重複するため、タグ起動の結果を確認する。
