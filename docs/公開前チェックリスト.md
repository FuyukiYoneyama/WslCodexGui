# 公開前チェックリスト

このリポジトリをpublicにし、`v1.0.0`としてバイナリを配布するまでに必要な作業をまとめる。

作成日: 2026-08-10（ソース側 `0.5.21` 時点）
位置づけ: [残項目.md](残項目.md)が「機能・品質として未完了なもの」を扱うのに対し、本書は**配布物としての完成処理**を扱う。両者は目的が異なるため分けている。

## 前提となる判断

コードそのものについては、**公開できないほど足りない機能はほぼ無い**。いま足りないのは配布物としての仕上げである。特に次の4つが終われば公開して差し支えない段階になる。

```text
Git履歴の公開監査 → third-party licenses → インストーラ → クリーンPC試験
```

逆に、この段階で`App.tsx`の分割や新機能に着手すると公開が遠のく。**機能開発を止めてリリース工程へ移る**のが適切である（`App.tsx`分割と`-32001`自動retryはVer.1.1以降のままでよい。巨大threadの実用上の性能問題は`0.5.21`でほぼ解消済み）。

## A. 公開前に必須

### A-1. 公開用リポジトリの情報漏洩監査 ★最重要

これまで実機検証の記録として、Windowsユーザー名・ホスト名・`C:\Users\...`・`/home/user/...`・WSLのgateway IP・実アカウントのクレジット残高・実機固有パス・誤コミットした`app.exe`などが記録されてきた。**現在のファイルを直すだけでは過去コミットからは消えない**ため、Git履歴全体の監査が要る。

判断は次の3分類で行う。

```text
公開可能
公開したくないが秘密ではない
絶対に公開してはいけない
```

APIキーらしき文字列は簡易検索では見つかっていないが、それは履歴監査の代わりにはならない。

#### 予備調査の結果（2026-08-10 実施）

現時点で機械的に確認できた事実を記録する。**これは予備調査であり、本監査の代替ではない。**

| 対象 | 現在のファイル | 履歴 |
| --- | --- | --- |
| `user`（Windowsユーザー名） | 3ファイル | 7コミット |
| `user`（WSLユーザー名） | 16ファイル | 19コミット |
| `C:\Users` | — | 10コミット |
| クレジット残高 `1234.5678900000` | 3ファイル | 1コミット |
| WSL gateway `172.21.112.1` | 3ファイル | — |
| 誤コミットした`app.exe` | 追跡停止済み | **8個のblobが履歴に残存（各約10MB、計約80MB）** |

個別に判断が要るもの:

- **`app/src-tauri/tauri.conf.json` の `identifier: "com.user.wslcodexgui"`** — バンドル識別子にユーザー名が入っている。これは実害の少ない情報だが、**公開後に変更するとアップグレード経路が壊れる**ため、変更するなら`v1.0.0`タグの前に決める必要がある。
- **クレジット残高** — [creditBadge.test.mjs](../app/src/creditBadge.test.mjs)・[creditBadge.ts](../app/src/creditBadge.ts)・[残項目.md](残項目.md)に実アカウントの残高が実データとして入っている。テストの値としては架空の数値で十分機能するため、差し替えるのが妥当。
- **WSL gateway IP** — [lib.rs](../app/src-tauri/src/lib.rs)のテスト値と仕様書の記録。`172.21.112.1`はWSLが割り当てるプライベートアドレスで秘密性は低いが、環境の特定に繋がるため「公開したくないが秘密ではない」に該当する。
- **`app.exe`のblob** — 履歴から消すにはリポジトリの書き換え（`git filter-repo`等）が必要。単独開発でforkも無いため実行は容易だが、コミットSHAがすべて変わる。**publicにする前に行うこと**（public化後の書き換えは、既にcloneされた履歴を回収できない）。

#### 進め方

1. 分類基準を決める（上記3分類）
2. 現在のファイルを是正する
3. 履歴の書き換えが必要なものを確定する（`app.exe` blobは確定、それ以外は分類次第）
4. 書き換えを実行し、ローカルで結果を検証する
5. **その後に**public化する

**→ 1〜4は完了（2026-10-24）**: ユーザーの判断で、Windows/WSLのユーザー名（小文字の単語として）を`user`に、実アカウントの残高を架空の値に置き換え、`target/release/app.exe`を全履歴から削除した（`git filter-repo`）。バンドル識別子は書き換えの直前に`io.github.fuyukiyoneyama.wslcodexgui`へ変更済み。作者名・作者アドレス（元から全コミットがGitHubのnoreplyアドレス）とGitHubユーザー名、WSLのgateway IPはそのまま。書き換え後の履歴は新しい非公開リポジトリ`FuyukiYoneyama/WslCodexGui`へ入れ直し、元のリポジトリは`FuyukiYoneyama/WslCodexGui-old`（非公開）として残した。public化（5）は他の項目が終わってから。

### A-2. 正式なthird-party license通知

MIT LICENSE自体に問題はない。ただし[THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md)が自ら次のように明記している。

> 本ドキュメントはその要件を満たす完全な通知文書ではなく、あくまで調査結果の要約である。

Apache-2.0・BSD-3-Clause・MPL-2.0などは、配布物に著作権表示とライセンス全文の同梱を要求する。**バイナリを公開するなら必須**である。`cargo about`・`license-checker`等で全依存関係のライセンス全文を機械的に収集し、正式な通知ファイルとして同梱する。

**→ 完了（2026-10-24、0.5.55）**: [generate-third-party-licenses.mjs](../app/scripts/generate-third-party-licenses.mjs)で[THIRD-PARTY-LICENSES.txt](../THIRD-PARTY-LICENSES.txt)（Rustクレート224件・npmパッケージ109件、約220KB）を生成し、MSI・NSISの両インストーラに`LICENSE`とともに同梱した。リリース前に`node scripts/generate-third-party-licenses.mjs --check`で最新であることを確認すること。

### A-3. 本物のインストーラを作り、試す

初回のGitHub ReleaseはNSISインストーラのみを配布する方針。`0.5.59`で新規インストール・更新・アンインストールを実機試験済み。`0.5.60`からビルド対象をNSISのみに設定し、NSIS成果物の生成を確認した。

公開するなら次を実際に確認する。

- 新規インストール
- 上書き更新（前バージョンからのアップグレード）
- アンインストール

**ここが公開前の最大の品質ゲートである。**

**→ NSISの実機試験は完了（2026-10-24、0.5.59）**: 通常のExplorerからセットアップを起動し、0.5.58の新規インストール、0.5.59への更新、0.5.59のアンインストール（アプリデータ保持）、0.5.59の再配置を確認した。最終状態は0.5.59をインストール済み。更新後の実行ファイルのバージョン、ブランドアイコンのExplorer表示、デスクトップショートカットからの起動、旧版ICOの削除を確認した。さらにユーザー提示の実デスクトップ画像で青緑のブランドアイコンを確認し、ユーザーから起動できるとの報告を受けた。Codexのコマンド実行経路からセットアップを起動した回では、通常のExplorerからインストール先を参照できず、ショートカットが白い標準アイコンになった。【推定】Codexパッケージ領域への仮想化が原因。実機試験ではExplorerから起動する。詳細は[残項目.mdの完了ログ](残項目.md#完了ログ)。最終配布版のNSIS成果物は、1.0.0への版数統一後に改めて生成・確認する。

### A-4. クリーンPC試験

開発PCにはRust・Node・MSVC・Codex・WSL・過去のビルド成果物・npm/Cargoキャッシュが揃っている。公開版で最も怖いのは**開発PCでは偶然動く**状態である。

最低一度、次を通す。

```text
アプリ未導入
↓
インストーラ
↓
初回起動
↓
Codex検出
↓
接続
↓
thread作成
↓
turn完了
↓
アンインストール
```

**ここで初めて、リリース前CIを1回走らせる**（[CI運用方針](#ci運用方針との関係)参照）。

### A-5. GUI障害試験の判定

[残項目.md](残項目.md)に残っている実機試験。コードレビューでは代替できない。

- 承認要求中に切断
- 承認応答のwrite失敗 → 同一request IDで再試行
- 画像保存直後の送信防止
- 画像保存中のthread切替／切断

承認と画像は`React state / Tauri IPC / Codex app-server / 一時ファイル / 非同期event`をまたぐため、公開前に実機で終わらせる価値がある。

**→ 判定済み（2026-10-24、0.5.56）**: 画像の2件は合格。承認中の切断は、ダイアログが切断ボタンを覆う設計であり、ユーザー判断で現状維持。代替としてプロセス終了による切断を試し、ダイアログ消去と再接続を確認した。書込み失敗だけを起こす状況はGUIで再現できず、失敗時にダイアログを残すコードを確認した。両件の制約は記録済みで、追加の公開ゲートにはしない。試験中に見つかった「予期しない切断後に送信が`thread not found`で失敗し入力が消える」不具合と「切断の通知がない」問題は0.5.56で修正済み。詳細は[残項目.md](残項目.md)の完了ログ。

## C. 必須ではないもの

### C-1. コード署名

公開自体に必須ではない。未署名でもGitHub Releaseから配布できる。ただしWindows SmartScreenが「発行元不明」等の警告を出す可能性がある。

最初は**未署名である旨をREADMEとReleaseに明記して公開し**、利用者が増えてから署名を検討すればよい。個人開発で最初から証明書費用を負担する必要はない。

### C-2. SECURITY.md

あると良いが必須ではない。作るなら「脆弱性は公開Issueではなく○○へ報告」「対応対象バージョン」程度で十分。**メールアドレスを公開したくないなら無理に置かなくてよい。**

### C-3. CONTRIBUTING.md

一人開発で外部PRを積極的に募集しないなら不要。READMEに「Issues歓迎」「PRは事前にIssueで相談」程度でよい。

### C-4. 着手しないもの

- **`App.tsx`の分割** — 公開を止める理由にならない。Ver.1.1以降のまま。
- **`-32001`自動retry** — 不要。現在の（再送しない）方が安全。

## CI運用方針との関係

[CI運用方針](残項目.md)により、通常開発でGitHub Actionsは使わない。workflowは`workflow_dispatch`（手動）と`push: tags: ["v*"]`（リリースタグ）でのみ起動する。

上記手順6の`v1.0.0`タグpushでCIを起動する。目的は「クリーンなGitHub環境でもリリース対象がビルド・テストできること」の確認。`workflow_dispatch`も実行すると重複するため、タグ起動の結果を確認する。
